# 阅读笔记

## 一句话总结

自我改进的近期现实路径，可能不是模型直接改写自身权重，而是让模型不断改进包裹它的 harness：工作流、上下文、工具、记忆、权限和评估。

## 关键概念

- **Harness**：基础模型之外的执行系统，负责工具调用、上下文、状态、权限、评估和结果管理。
- **Meta-methodology**：优化“如何得到更好答案”的机制，而不是只优化某一次答案。
- **文件系统作为记忆**：把长任务产物留在可寻址、可恢复的外部状态里，而不是全塞进上下文。
- **Context engineering**：为长任务构造、维护、压缩和更新上下文的系统层。
- **Self-Harness**：从失败轨迹中挖掘弱点，提出 harness 修改，再用验证集筛选可接受改动。
- **Evolutionary search**：在 prompt、workflow、程序或 harness 的候选集合中生成变体、评估、筛选和迭代。
- **评估器边界**：自我改进循环不能完全控制自己的奖励函数、权限系统和关键安全检查。

## 文章主张

1. Harness 工程已经从 prompt 模板进入 runtime 和软件系统设计层。
2. 近期 RSI 更可能先发生在 harness、workflow、context 和 tool-use 层，而不是模型直接自改权重。
3. Coding agent 是观察 harness 演进的好样本，因为它天然依赖文件、shell、测试、版本控制和外部反馈。
4. Context 不应该只是不断加长的 prompt，而应该是可更新、可检索、可评估的结构化资源。
5. Workflow 和 harness 一旦被表示为代码，就可以成为 agent 搜索、变异和优化的对象。
6. 自我改进系统最大的风险来自错误评估、短期目标、奖励投机、权限失控和人类监督位置不当。

## 我的理解

这篇文章把很多看似分散的 agent 研究放到同一个坐标系里了：它们都在优化“模型之外的机制”。有的工作优化上下文，有的优化 workflow，有的优化 prompt，有的优化 harness code，有的优化产生优化器的程序。表面看是不同方向，底层都是在回答一个问题：基础模型每一次被调用之前、调用期间、调用之后，系统应该如何组织信息、行动和反馈。

我最喜欢的是它把 harness 和 OS 类比。这个类比非常准确。真正能让 agent 可靠工作的东西，往往不是某个神奇 prompt，而是权限、文件、进程、缓存、状态、日志、恢复、评估和用户触点这些沉默的系统设计。模型越强，这层系统反而越重要，因为它决定模型能力被放大到哪里，也决定错误会不会被同样放大。

文章也提醒了一个容易被忽视的问题：一旦让 agent 优化 harness，就必须先回答“它可以改哪里，不能改哪里”。如果评估器、权限边界、审计机制也在同一个可自改循环里，系统就会把工程问题变成安全问题。

## 对 agent 工程的启发

- Agent 产品的核心资产不只是模型调用，而是 harness：任务循环、工具接口、状态管理、权限、日志、评估和恢复策略。
- 文件系统和结构化 artifact 应该是一等公民。长任务不能依赖上下文窗口记住全部历史。
- 子 agent 的结果最好有持久地址和状态记录，否则并行会变成不可审计的临时噪声。
- Context 压缩不应该只追求短，还要保留可追溯路径和失败经验。
- Harness 的可编辑表面要窄，权限、密钥、评估器和安全审计应当位于自改循环之外。
- 对 coding agent 来说，长期仓库健康需要单独设计反馈信号，不能只用短期测试通过率代替。

## 与 #6 的呼应

#6 的 Peter Pang 文章更偏工程落地：云端 agent 要把用户状态、runner 代码、密钥和触发入口拆开。#7 这篇则提供更高层框架：这些拆分都属于 harness 设计。两篇放在一起读，一个讲“harness 为什么会成为自我改进对象”，一个讲“把 agent 放到云上后，harness 的边界必须怎么画”。

## 可延伸思考

- Harness 的最小可优化单元是什么：prompt、tool schema、workflow graph、状态机，还是一组代码模块？
- 如果 agent 可以提出 harness 改动，哪些改动必须经过人类 review？
- 如何保存失败轨迹，才能既帮助未来搜索，又不会让上下文管理失控？
- 长期仓库健康能否被拆成可评估的 proxy，而不是只靠人类 reviewer 的直觉？
- 是否应该把权限、评估器和审计记录建成 harness 外部的“不可自改内核”？

## 待补充问题

- Meta-Harness、Self-Harness 这类系统在真实生产 agent 中最先会落到哪个边界？
- 对云端 agent 来说，harness 自改和平台升级如何避免互相干扰？
- 如果不同模型需要不同 harness，平台应该维护模型专属 harness，还是维护可配置 harness？
- 人类监督的最佳抽象层是什么：任务目标、规格、失败聚类、harness diff，还是最终结果？
