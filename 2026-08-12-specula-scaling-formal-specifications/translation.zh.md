# Specula：扩展形式化规约，实现对系统代码的自主模型检查

> 原文：[Specula: Scaling formal specifications for autonomous model checking of system code](https://muratbuffalo.blogspot.com/2026/08/specula-scaling-formal-specifications.html)  
> 作者：Murat Demirbas  
> 发布日期：2026-08-12  
> 说明：以下全文根据用户于 2026-08-16 提供的英文正文忠实翻译，保留原文的段落顺序、数据、语气与附记。

Specula 是一个智能体系统，它通过为代码编写规约并对规约进行模型检查，将软件 bug 查找过程自动化。它从代码中自动推导 TLA+ 规约，通过轨迹验证（trace validation）检查代码与规约的一致性，对规约进行模型检查以发现并发 bug，并通过编写具有精确时序的集成测试，在代码层复现 bug。

我记得自己在 2000 年读到 Daikon 论文《[快速检测相关的程序不变量](https://dl.acm.org/doi/abs/10.1145/337180.337240)》（Quickly detecting relevant program invariants）时深受震撼。26 年后，在我主 2026 年，我们竟然已经能以一键式方式端到端地解决这个问题，而且做得远超我曾经认为可能达到的程度。

但不知为何，我仍然对这篇论文有些不满足。也许是我过于苛刻，想通过[与论文争论](https://muratbuffalo.blogspot.com/2013/07/how-i-read-research-paper.html)从中获得更多东西。所以请耐心听我说下去，直到我随着时间解决这些问题——或者学会接受它们。我认识 Specula 工作的许多作者，也尊重他们；我知道他们不会错误地理解我对这个更大问题的批评……我只是在努力弄清这片领域的版图。

那么，让我们先看看 Specula 做对了什么、它有哪些主要贡献，然后再深入讨论我尚未解决的问题，以及我对这片领域近乎存在主义式的思考。

## 为什么 Specula 是一项令人印象深刻的成就

Specula 在 48 个复杂开源分布式与并发系统的“切片”上运行，其中包括 MongoDB、微软的 SONiC 网络操作系统、GCC 的 `libgomp`、Etcd，以及 RabbitMQ 的 `ra`。它发现了 249 个 bug，其中 207 个是新发现。48 个系统横跨 7 种语言，从 C 到 Erlang，再到 Rust。这非常令人印象深刻，也配得上论文标题中的“扩展”（scaling）一词。手工编写 TLA+ 规约可能需要数周时间——对于不熟悉的代码库尤其如此——而 Specula 可以在 1.4 到 9.8 小时内完成端到端检查，每个系统的 token 成本中位数为 57 美元。我有没有说过，这一切都是一键式的？开发者只需审查最终结果。他们甚至可能根本不必查看 TLA+ 规约，只需检查报告出来的 bug，再决定如何处理即可。

好吧，确实令人印象深刻。下面深入看看这里的技术新意。据我理解，这项技术的新意来自两股对立力量在自我演化循环中彼此角力，从而产生一种“铁磨铁”的效果。轨迹验证把规约拉向代码，而模型检查则向相反方向施力。两股力量缺一不可，因为任何一方单独工作都会受骗。如果只有轨迹验证作为奖励信号，智能体就会进行奖励投机（reward hacking）：它会放宽规约中的 guard、添加通配符，或者硬编码只针对特定轨迹的更新，只为了让日志能够重放。例如，在 Kudu-Raft 应用中，智能体“修复”了 follower 的接受路径，让它无条件覆盖日志后缀；轨迹于是重放得非常漂亮，接着状态机安全性（State Machine Safety）一步就抓住了问题。模型检查会检查规约/模型中不存在非法行为。Specula 把这两者接入自我演化循环：每次迭代都会向智能体提供新证据、反例、模型与代码之间的缺口，或者一次失败的复现，并迫使它重新思考。简而言之，这些循环把一个不可靠的智能体变成了一个可靠的智能体。

为了评估这项技术新意，他们用三种方式运行了相同的提示：原生 Claude Code、配备官方 TLA+ skill 和 MCP server 的 Claude Code，以及 Specula。在五个系统上，Specula 找到 62 个 bug，原生版本找到 2 个，配备 TLA+ 的版本也只找到 3 个。因此，把整套 TLA+ 工具链交给一个前沿智能体并不能带来多少收益，而 Specula 把这个基线远远甩在身后。正如作者所说，缺少的不是 TLA+ 知识，而是让智能体能够修复自己所写内容的运行时反馈。我认为，评估中的巨大差距说明，Specula 的技术贡献不在于提示工程或炒作 LLM，也不只是给 LLM 一个模型检查器。

但我的问题在于，我无法用一种非常稳健、扎实而具体的方式指出这项技术贡献究竟是什么。可以说，这项技术贡献似乎是从一组（某种程度上并不健全的）启发式规则中自行涌现出来的。让我试着解释一下……

## 同义反复问题：如何从有 bug 的代码中推断意图？

Specula 把系统 artifact（代码、Git 提交历史、PR、注释）视为推导不变量的基准真相。它的 87% 不变量可以追溯到实现代码和注释，74% 可以追溯到 issue tracker，而只有 20% 可以追溯到文档。也就是说，规约推导以代码为来源，而那里也正是 bug 所在的地方。那么，如果 Specula 把代码库当作基准真相，它究竟如何发现 bug？它难道不会直接把现有 bug 复制进模型，把它们当成预期行为吗？是什么阻止了这种情况？

Leslie Lamport 永远不会理解这种做法……你需要一份独立的需求规约，以及与之分离的代码。对形式化方法从业者来说，编写规约本身**就是**理解问题；之后写代码反而是容易的部分。Specula 把这个过程倒了过来：代码已经给定，再从中重建理解。但这样一来，“规约”一词表达的东西就与 Lamport 世界——也就是形式化方法和数学的世界——中的含义不同，而论文从未讨论这一点。

也正是在这里，术语开始滑动。在一致性循环中，论文考虑三种情况：模型/规约不正确、代码存在 bug，或者不变量不正确。相对于什么而言不正确？？对模型/规约来说，答案是相对于代码；对代码来说，答案是相对于模型/规约。注意到其中的循环了吗？至于不变量，则根本没有外部参照点！当一个不变量被判定为不正确时，它是相对于智能体自己对 artifact 的解读而被判错的；随后又由智能体修订，并由智能体选择的证据来证明修订合理。智能体，智能体，还是智能体！

据我理解，论文给出的实际答案是：当各种 artifact 彼此不一致时，规约就会识别出 bug。Specula 的场景生成试图捕捉这些不一致。但如果设计本身就是错的，而且每个人都一致地把它写了下来，那就无从发现。如果智能体朝另一个方向误读了一条含义模糊的注释，它就会悄无声息地放宽一个真实不变量，让它去匹配代码缺陷，而你永远不会知道。

## 这是使用推断规约的智能模糊测试吗？

他们在一台 Azure VM 上运行所有这些工作：96 核 AMD EPYC 9V74、384GB RAM，并用拥有 100 万上下文窗口、开启最大推理强度的 Opus 4.8 驱动 Claude Code。即便使用这样的机器，Specula 也不会对完整参考规约进行模型检查，因为那会导致状态空间爆炸。相反，它运用一些技巧，把问题投影到前面提到的逐场景模型中：限制一个动作可以触发多少次（例如，崩溃动作的 `bound=0` 意味着只检查 happy path），把多步骤过程粗化为一个原子动作，并把动作对串行化为固定顺序。

这三种方法都是合理技术，人类建模者也都会使用。令我困扰的是，论文没有为其中任何一种提供论证。为什么是这三种操作？只有当某个性质不观察中间状态时，对动作进行粗化才是健全的；那么，哪些不变量能经受住哪些粗化？论文只说中间状态被抽象掉，然后便继续往下讲。人类专家做出这种判断时，心里会有一套理由。我不确定让智能体以自动方式尝试这些操作是否可靠。这听起来更加临时拼凑，像是在对系统进行智能模糊测试。

协议级与代码级的划分给我同样的感觉，而且我认为它更加关键，因为它承担着整个论证的重量。整个反奖励投机论证，都依赖协议级不变量独立于智能体刚刚建模的代码。论文给出了一个例子：Etcd-Raft 得到的是“已提交条目位于持久存储中”，而 MongoDB 得到的是更弱的“一个条目在被报告为已提交之前，已经存在于服务器自己的日志中”；这是因为 MongoDB 为了降低写延迟而有意偏离 Raft，智能体从修订历史中挖出了这一点。很好。因此，协议级表示它对任何合规实现都成立，而代码级表示这是当前实现所作出的承诺。可问题是，Specula 只有 21.1% 的不变量属于协议级；其余 78.9% 都是从与模型相同的 artifact 中挖掘出来的代码级不变量。所以，防止过拟合的护栏只建立在五分之一的不变量上，而由智能体自己决定哪五分之一属于这一类，并且没有任何东西检查这个决定。如果把一段对当前代码的描述错误分类为协议级不变量，那么你现在就是在用一个已经遭到奖励投机的 artifact 防范奖励投机。这本质上是我对“从代码生成规约会形成循环”这一批评的更尖锐版本。更让我担忧的是，从图 3.a 和图 3.b 来看，我看不出两种不变量之间有任何结构或性质上的差别，因此这种区分显得更加临时拼凑，也很容易变得模糊或混淆。

然后还有收敛问题。论文说这些演化循环是安全的，并且 Specula“在智能体会随迭代不断改进这一假设下提供收敛性”。这并不能让人安心，因为所有工作都由这个假设承担了。论文所说的坏不变量失效模式，就是过程根本不收敛、不断迭代，而在实践中你会用时间或 token 预算把它停下来。他们的数据比我预想的更好：所有记录下来的运行都收敛了；插桩问题在三轮之内修复；91.3% 的不变量和模型错误在一次迭代中修复；没有任何一个超过四轮。唯一需要四轮的案例是 SONiC 的链路管理器。智能体写下了一个不变量，声称一条链路的两个 gateway 永远不会同时处于 standby。模型检查却不断发现两者同时处于 standby 的状态：一种是故障转移正处在交接中途，另一种是两个 gateway 都无法接管的降级模式。这些状态是合法的，只是暂时的。经历四个反例后，智能体才不再把它们称为 bug，转而修复自己的不变量。因此，自我演化循环再一次奏效了。但这也表明，要区分真实 bug 和只是看起来坏掉的状态有多么困难。

我的意思是，这一切都很实用主义，而这没什么不好。但真正让我难受的是，这些方法缺少原则性的论证，而且论文引入和描述它们的方式也十分临时拼凑。也许这就是我们正在做的新科学……一种更偏启发式的计算机科学，其中还混合着人类学——好吧，既然研究的是智能体，那就叫智能体学（agentology）。也许未来的论文将主要由田野笔记组成，记录智能体如何行为失常，以及哪些护栏能够阻止它们。

不可否认，Opus 在 Specula 中承担了大量繁重工作，作者也坦率承认这一点。换成 Sonnet 4.6 后，Specula 在那 62 个 bug 中只能找到 10 个，所需实际时间几乎相同，成本是原来的 61%，所以每个 bug 的成本是 59 美元，而不是 16 美元。换成 Haiku 4.5 后，它一个 bug 也找不到，而且总是在任务尚未完成时就宣布完成。差距也体现在规约质量评分中：Haiku 写出的 TLA+ 语法仍有 95% 正确，但不变量得分只有 17%。不过，看看这一部分进展得有多快。[我评述 SysMoBench 时](https://muratbuffalo.blogspot.com/2026/03/sysmobench-evaluating-ai-on-formally.html)，这个同一团队在 2026 年 1 月推出的 benchmark 还需要作者把不变量模板交给 LLM，只要求它将模板映射到自己的变量名，因为不变量是规约中信号最密集的部分。现在，Specula 已经能让智能体在无人协助的情况下从提交历史中推导不变量。

## 大局

Specula 是一个很棒的实用主义想法，而且在它所做的事情上确实有效。我的批评主要是希望更准确地命名这些贡献和机制，同时也想做最后一次努力，尝试从这些方法中去掉临时拼凑的成分。我也应该诚实说明，这种努力源自哪里。当我们以后真正开始撰写自己关于智能体式、基于规约的开发论文时，我确信我们会采用同一类启发式方法，而我也会发现自己用现在所抱怨的同一种含糊其词来为它们辩护。这才是真正困扰我的地方。我甚至不知道这篇论文的非临时拼凑版本究竟会是什么样子。

尽管如此，即使只从实用层面看，仍有许多问题需要解决，因为 Specula 绕开了真正困难的问题：组合。Specula 避免为多服务代码库编写组合式规约，也避免用这类规约进行推理。它在编写规约时没有采用组合式验证或假设—保证推理，因为这些规约是系统的[单体横切片](https://muratbuffalo.blogspot.com/2026/05/the-two-abstractions-of-system-design.html)。对于拥有多个服务的系统，例如由 5 个不同 daemon 组成的 SONiC，Specula 为每个模块建立一个模型，并在场景模型内部模拟跨服务交互。因此，它无法说明每个模块的保证加起来是否构成系统级保证。遗憾的是，在分布式系统里，你真正害怕的[故障](https://muratbuffalo.blogspot.com/2026/07/characterizing-metastable-faults-and.html)正是那些[跨边界故障](https://muratbuffalo.blogspot.com/2026/08/towards-designing-execution-control.html)，尤其是与恢复有关的故障。
