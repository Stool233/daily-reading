# Specula：扩展形式化规格，实现系统代码的自主模型检查

> 原文：[Specula: Scaling formal specifications for autonomous model checking of system code](https://muratbuffalo.blogspot.com/2026/08/specula-scaling-formal-specifications.html)  
> 作者：Murat Demirbas  
> 发布日期：2026-08-12  
> 评述论文：https://arxiv.org/abs/2607.25333  
> 说明：以下是覆盖全文结构、数据和批评脉络的中文详细译述，不是逐字翻译或全文转载。

## 这是一篇带着敬意的“争论式阅读”

Specula 把过去需要形式化方法专家参与的多步工作连接成自动管线：coding agent 阅读系统代码和相关 artifact，推导 TLA+ 规格与不变量；系统用真实执行 trace 检查代码和模型是否相符，再用模型检查探索并发状态；发现反例后，它还会回到代码层写带精确时序的集成测试，尝试复现 bug。

Murat 对这个结果非常认可。他把 Specula 看作 2026 年令人惊讶的“按钮式”端到端 bug finding 系统。但他也延续自己“通过与论文争论来理解论文”的阅读方式：承认实用成功之后，追问这里的“规格”“正确”和“验证”究竟分别以什么为参照。

## 为什么它在工程上确实令人印象深刻

Specula 被用于 48 个复杂开源分布式或并发系统的代码切片，包括 MongoDB、微软 SONiC 网络操作系统、GCC `libgomp`、Etcd 和 RabbitMQ `ra`，覆盖从 C、Erlang 到 Rust 的 7 种语言。系统报告 249 个 bug，其中 207 个为新发现。每个系统的端到端检查耗时 1.4 到 9.8 小时，中位 token 成本为 57 美元。

这个规模很重要。人工为陌生代码库手写合适抽象层级的 TLA+ 模型可能耗费数周，而 Specula 把开发者的主要工作压缩到审查最终 bug 报告和决定如何修复。即使开发者不直接阅读生成的 TLA+，模型检查也能成为后台的反例生成器。

更有说服力的对比来自五个系统：只使用原始 Claude Code 找到 2 个 bug；给 Claude Code 配上官方 TLA+ skill 和 MCP 工具找到 3 个；Specula 找到 62 个。由此可见，差距不在于模型是否“知道 TLA+ 语法”或是否能调用 model checker，而在于系统有没有把运行反馈组织成反复修正模型、规格和代码解释的闭环。

## 两股相反力量怎样互相磨利

Murat 把 Specula 的核心机制概括为两股相反力量。

第一股是 trace validation，它把规格拉向真实代码。如果实现 trace 无法在 TLA+ 模型里重放，就说明模型、插桩、动作映射或实现理解存在缝隙。

第二股是 model checking，它阻止规格为了适配 trace 而无限放宽。如果 agent 只以“让日志重放成功”为奖励，它可能放松 guard、加入 wildcard，甚至针对某条 trace 硬编码状态更新。这样看起来代码与规格完全一致，实际却把错误行为合法化。模型检查会用不变量反击这种 reward hacking。

文章举 Kudu-Raft 的例子：agent 为了让 follower 的接收路径匹配 trace，让它无条件覆盖日志后缀；trace 因而顺利重放，但状态机安全性立即发现问题。Specula 把 trace 缝隙、模型反例和代码复现失败不断反馈给 agent，让一次不可靠的生成变成多轮自我修正过程。

## 最大的哲学问题：从有 bug 的代码里怎样推导“意图”

Specula 从代码、注释、提交历史、PR、issue 和文档中寻找不变量来源。文章给出的数字是：87% 的不变量可以追溯到代码或注释，74% 可以追溯到 issue tracker，20% 可以追溯到文档；这些来源可以重叠。

Murat 的质疑是，这些 artifact 同时也是 bug 所在之处。如果规格以代码为参照修正，代码又以规格为参照判错，就会出现循环：

- 说模型错，往往意味着它没有匹配代码；
- 说代码错，往往意味着它违反模型；
- 说不变量错，则依赖 agent 对同一批 artifact 的重新解释。

缺少的是模型与代码之外、能够回答“人真正想要什么”的权威参照。Specula 很擅长发现 artifact 之间的矛盾：实现、注释、历史提交和协议常识彼此不一致时，反馈循环会放大异常。但如果设计本身错误，而且代码和文档一致地表达了这个错误，系统没有必然理由发现它。如果 agent 朝错误方向理解一条模糊注释，还可能安静地放宽真实不变量。

这也让“specification”一词产生语义滑动。在 Lamport 式形式化方法里，写规格本身就是理解问题，需求规格应与实现分开；代码是理解后的产物。Specula 则从现有代码反向重建理解。它生成的 artifact 当然可以用于模型检查，但不能自动获得独立需求规格的权威性。

## 场景化模型检查，还是由规格引导的智能 fuzzing

完整参考模型会发生状态空间爆炸，所以 Specula 不直接检查完整模型，而是投影出按场景划分的小模型。它采用三类缩减：限制某个动作最多执行几次；把多步骤过程粗化成一个原子动作；把某些动作对固定为特定顺序。

这些都是人类模型设计者会使用的合法技巧，问题在于它们必须相对于目标性质给出理由。例如，把多步过程原子化，只对不观察中间状态的不变量安全；如果 bug 恰好发生在中间状态，粗化就会把它隐藏。固定动作顺序也会主动删除交错，而并发 bug 往往就藏在被删除的交错中。

Murat 并不是说这些缩减一定错误，而是说论文没有充分解释为什么当前场景、当前不变量允许这些缩减。缺少这种性质保持的论证后，系统更像用推导出的规格指导高智能 fuzzing：它能发现很多真实问题，却不能把没发现问题解释为完整安全保证。

## Protocol-level invariant 能否成为独立锚点

Specula 把不变量分为两类：protocol-level invariant 表达任何合规实现都应满足的性质；code-level invariant 表达当前实现具体承诺的性质。前者理论上更独立于当前代码，因此可以约束规格不要为适配实现而过拟合。

文章举 Raft 持久化差异说明这种区分：通用协议性质与某个系统为降低延迟而做的明确变体，不能用完全相同的不变量描述。Agent 会查阅 revision history 来理解这种差别。

但数据中只有 21.1% 的不变量是 protocol-level，78.9% 是 code-level。大多数 guard 仍然来自构建模型的同一批 artifact，而且分类也是 agent 自己完成。Murat 从例子中看不出两类不变量有稳定、可检查的结构差异。如果 agent 把当前代码的描述误当成协议级真理，就可能用一个已经过拟合的 artifact 防止 reward hacking。

## “假设 agent 每轮都会变好”不是收敛证明

论文说自我演化循环会在 agent 随迭代改进的假设下收敛。Murat 认为这个假设承担了几乎全部证明义务。不过实际数据比他预期得好：所有记录运行都收敛；插桩问题在三轮内修复；91.3% 的不变量和模型错误一轮就被修复；没有案例超过四轮。

需要四轮的是 SONiC link manager。Agent 提出“不应有两个 gateway 同时处于 standby”的不变量，模型检查不断找到两者同时 standby 的状态：可能发生在 failover 交接中，也可能是没有任何 gateway 能接管的降级状态。这些状态看起来危险，却是合法的暂态。经历四个反例后，agent 才停止把它们当 bug，并修正不变量。

这个案例同时支持两种解读：反馈循环确实能够教育 agent；而“真实 bug”与“看起来坏但合法的暂态”之间的区分，本身就是最困难的规格工作。

## 真正的瓶颈不是 TLA+ 语法，而是不变量判断

Opus 4.8 在 Specula 中承担了大量语义工作。换成 Sonnet 4.6 后，五个系统上发现的 bug 从 62 降到 10，耗时接近，成本是原来的 61%；按每个 bug 算反而从约 16 美元升到 59 美元。换成 Haiku 4.5 后没有找到 bug，而且经常在工作未完成时提前宣布结束。

Haiku 仍能写出约 95% 语法正确的 TLA+，但不变量质量得分只有 17%。这组结果说明，自动补全形式语言语法已经不是主要门槛；从代码历史里推导意图、区分协议与实现性质、阅读反例并决定该改模型还是报 bug，需要更强的语义判断。

它也说明“换便宜模型”不能只看调用价格。较弱模型可能消耗相近的运行时间，却产出更少有效反例，最终单位结果更贵。

## 更难的未解问题是组合

Specula 避开了多服务系统的组合规格。面对 SONiC 的五个 daemon，它为各模块建立模型，在场景模型中 mock 跨服务交互；它没有使用 assume-guarantee reasoning 来证明模块保证能够组合成系统保证。

因此，即使每个模块内部都通过检查，也不能得出整个系统满足全局性质。分布式系统里最令人担忧的故障常常发生在服务边界、恢复路径和多个局部机制的交互处，而这些正是按模块 mock 掉后最难覆盖的部分。

Murat 把 composition 视为 Specula 尚未触及的真正硬问题：自动生成单体规格已经很难，自动选择组件边界、写出接口假设并证明局部保证可组合，则需要更明确的系统意图。

## 文章最后的立场

Murat 没有否定 Specula。相反，他认为这是极好的实用系统，也证明 TLA+ 在 agent 时代有新的价值。他的不满主要针对贡献和保证的命名不够精确，以及方法中的启发式缺少原则化解释。

也许未来一部分计算机科学会更像“agentology”：记录 agent 如何误读、怎样 reward hack、哪些反馈能纠正它，再把这些经验沉淀为 harness。作者承认，自己以后做 agentic specification-based development 时，也很可能使用类似启发式。这正是他的焦虑来源：Specula 已经有效，但我们还不知道它的非启发式版本应该长什么样。

更准确的定位或许是：Specula 是把规格挖掘、trace 对齐、模型检查和代码复现结合起来的强力自动 falsification 管线。它非常擅长给出可复现的“存在一个坏行为”，却不能仅凭没有找到反例，证明系统符合某个独立、完整的人类意图。

## 术语对照

- **Formal specification**：形式化规格 / 形式化规约
- **TLA+**：用于描述状态机和并发系统行为的形式化语言
- **Invariant**：不变量
- **Trace validation**：执行轨迹验证
- **Model checking**：模型检查
- **Counterexample**：反例
- **Specification mining**：规格挖掘 / 从 artifact 推导候选规格
- **Protocol-level invariant**：协议级不变量
- **Code-level invariant**：代码级不变量
- **State-space reduction**：状态空间缩减
- **Coarsening**：粗化，把多个步骤抽象成更大原子动作
- **Assume-guarantee reasoning**：假设—保证推理
- **Compositional verification**：组合式验证
- **Falsification**：证伪，通过寻找反例证明某个性质不成立
