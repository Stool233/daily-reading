# 阅读笔记

## 一句话总结

Specula 把 agent、TLA+、trace 和代码级复现组合成了极强的自动 bug-finding 闭环；它最强的能力是生成可信反例，最薄弱的环节仍是证明生成的不变量代表了独立、权威的人类意图。

## 关键概念

- **双向反馈**：trace validation 约束模型贴近实现，model checking 约束模型不能为贴合实现而任意放宽。
- **意图循环**：模型来自代码，代码又由模型判错，若没有外部需求就缺少最终参照。
- **规格来源（provenance）**：每条不变量应保留它来自协议、文档、issue、代码还是 agent 推断的证据链。
- **性质保持的抽象**：有界、原子化和固定交错只有在保留目标性质时才是可靠缩减。
- **反例驱动修正**：模型检查器不必理解语义，只需稳定地产生能迫使 agent 重新解释系统的证据。
- **证伪与验证的边界**：复现一个反例可以强有力地证明 bug 存在；搜索不到反例不等于证明系统符合完整意图。
- **组合缺口**：模块内部性质不能自动推出跨服务、跨恢复路径的系统性质。

## 最值得记住的数据

- 48 个开源系统切片，覆盖 7 种实现语言。
- 报告 249 个 bug，其中 207 个是新发现。
- 单系统端到端耗时 1.4–9.8 小时，中位 token 成本 57 美元。
- 五系统对比：原始 Claude Code 发现 2 个 bug，增加 TLA+ skill/MCP 后发现 3 个，Specula 发现 62 个。
- 不变量来源中，87% 可追溯到代码或注释，74% 可追溯到 issue tracker，20% 可追溯到文档；类别可重叠。
- 21.1% 为 protocol-level invariant，78.9% 为 code-level invariant。
- 91.3% 的不变量和模型错误在一轮内修正，没有案例超过四轮。
- Sonnet 版本发现 10 个 bug，Haiku 版本没有发现 bug；Haiku 的 TLA+ 语法正确率仍约 95%，不变量质量只有 17%。

## 把保证拆成不同层

| 层级 | 它回答的问题 | 不能自动回答的问题 |
| --- | --- | --- |
| TLA+ 语法检查 | 规格能否被工具解析 | 规格是否表达正确意图 |
| Trace validation | 已观察实现行为能否映射到模型 | 未观察行为是否正确；模型是否过度放宽 |
| Model checking | 场景模型内是否存在违反不变量的状态 | 不变量是否正确；被抽象掉的状态是否安全 |
| 代码级复现 | 模型反例能否在实现中触发 | 没复现是否说明反例不可能；修复是否完整 |
| 独立需求审查 | 不变量是否对应真正业务或协议意图 | 仍需处理需求本身的冲突与遗漏 |

把这些层混在一起，很容易把“工具跑通”“模型内部安全”“反例可复现”和“系统满足人类需求”误认为同一种正确性。Specula 的价值恰恰在于连接了前四层，但第五层仍不能由实现 artifact 自己提供。

## 我的理解

Murat 的循环论证批评是成立的，但它不必被解释为对 Specula 价值的否定。逆向规格挖掘天然缺少完整需求 oracle；与其要求它立即提供传统验证保证，不如把它看成一种把分散矛盾转化为可复现反例的系统。只要报告清楚规格来源、抽象边界和置信度，它仍然可能比普通测试或 fuzzing 更高效地发现深层并发 bug。

Specula 真正新颖的地方不一定是某个单独算法，而是反馈拓扑。给 Claude Code 加上 TLA+ 工具几乎没有提升，说明工具可用性不是瓶颈。系统必须决定何时用 trace 质疑模型、何时用模型检查质疑 agent、何时用代码复现质疑抽象。这正是 harness 工程：模型之外的循环决定模型能力能否转化为可靠结果。

最值得借鉴的是“让不同失败信号互相制约”。但这里的独立性有层次。Trace 和模型检查在操作上不同，可能减少局部 reward hacking；它们在意图来源上却可能同源，都建立在代码与 agent 推导的不变量上。因此，双重检查并不自动等于独立验证。

## Murat 的批评也需要限定

- 如果产品目标是找 bug 而不是证明无 bug，那么启发式缩减并非原罪；关键是不要把搜索覆盖包装成完备保证。
- 从代码反推规格虽不等于需求工程，却能发现实现、历史、issue、注释和协议常识之间的大量真实矛盾。
- 人类形式化建模同样依赖经验性抽象，只是专家通常能解释为什么某个抽象对目标性质安全。Agent 系统需要把这种解释变成显式 artifact，而不是假设启发式必须完全消失。
- “协议级”与“代码级”不变量并非越独立越好。实现特有性质对找真实回归同样重要；问题在于 provenance 和置信度是否透明。

## 与 Cursor 蜂群文章的共同主线

Cursor 认为，随着生成层级从代码行升到 swarm，稀缺资源会变成准确的意图描述。Specula 则试图从已经存在的代码和开发历史里重建这份描述。Murat 的批评指出了两者之间的硬边界：执行系统可以把规格放大成海量工作，却不能保证从实现中反推出来的规格就是原始意图。

两篇文章都发现“只给模型更多能力”不够。Cursor 需要任务树、VCS、设计文档、review lens 和 Field Guide；Specula 需要 trace validation、模型检查和代码复现循环。真正拉开差距的是 harness 如何生成反馈、保存事实和约束错误。

两篇还给出了一个关于独立 oracle 的对照。Cursor 的 SQLite swarm 不知道隐藏测试集，评分信号由外部固定；Specula 的大量不变量来自被检查的代码生态，评价信号与生成对象更相关。一个可推广的原则是：评估器越难被被评估系统改写或共同误解，反馈越可信。

## 与已有阅读的连接

- [形式化方法与编程的未来](../2026-06-07-formal-methods-and-the-future-of-programming/index.md) 认为 agent 降低了写规格与证明的成本，同时放大了验证需求。Specula 是这条判断的强案例，但也说明真正昂贵的部分从语法迁移到了不变量与意图。
- [用于自我改进的 Harness 工程](../2026-07-04-harness-engineering-for-self-improvement/index.md) 强调模型外反馈循环是近期自我改进的现实路径。Specula 的多轮 counterexample 修正正是这种机制，同时也暴露了评估器必须位于何种信任边界。

## 对 agent 与形式化方法工程的启发

- 每条生成不变量都应记录来源、推导理由、适用范围、置信度和反例历史。
- 区分“候选不变量”“已有人类确认的需求”“协议公理”和“当前实现行为”，不要把它们都叫 specification。
- 每次状态空间缩减都应生成 proof obligation 或至少一段性质保持说明。
- Bug 报告应标注保证等级：仅模型反例、trace 可达、代码可复现、维护者确认、已修复回归。
- 评估器和被优化对象应尽量分离；固定协议性质、隐藏测试、历史事故和人类批准的需求可作为外部锚点。
- 对跨服务系统，优先让 agent 生成接口假设与保证，再探索组合；只检查模块内部会漏掉最危险的边界故障。
- 便宜模型可以处理 TLA+ 语法和机械修改，语义模型应集中在不变量提议、反例解释和抽象审查。

## 可延伸思考

- 能否让多个独立 agent 分别从需求、代码、issue 和协议文献生成不变量，再只对交集与分歧做审查？
- 如何衡量两个反馈器是否真正独立，而不是只拥有不同工具界面？
- 场景缩减能否自动产生“此抽象对哪些不变量安全”的机器可检查证明？
- 如果一个不变量多轮无法收敛，系统应当继续搜索、降低置信度，还是请求人类裁决？
- 代码级反例复现失败，究竟应更新模型、测试调度还是 bug 置信度？
- 如何把跨服务恢复流程写成可组合的 assume-guarantee contract？

## 待补充问题
