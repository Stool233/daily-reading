## 原文提要

AAM 把一次任务作为授权单位，用短期、绑定发送方的凭证标识执行者。任务策略划定能力上限，工具运行环境与网络共同执行限制。Trust Ratchet（信任棘轮）依据受保护事件缩小整个任务执行图的权限，并要求限制生效后才向模型交付相关数据。日志为后续任务模板的权限复审提供证据，不能用来给当前任务自动扩权。人工审批也不能恢复已经撤销的能力。文章提出的是参考架构，多用户共享上下文中的端到端授权仍属于未解决的问题。[来源](https://blog.cloudflare.com/the-agent-access-model/)

## 阅读前先分清五个问题

下面是用于理解访问控制的概念划分，并非原文逐段改写。

| 问题 | 需要检查的内容 | 容易发生的误解 |
| --- | --- | --- |
| 谁在请求？ | 当前执行者及其身份凭据 | 知道执行者身份，就等于知道它的全部权限 |
| 它代表谁？ | 委托主体、当前代理和有效授权 | 在日志里记录一个用户名，就完成了委托 |
| 凭证能在哪里用？ | 目标资源服务器、受众和有效期 | token 对一个服务有效，对所有服务都有效 |
| 这次具体做什么？ | 操作、对象、参数、租户、接收方 | 能调用某个工具，就能使用它的任意参数 |
| 执行时条件还成立吗？ | 当前授权状态与相关前提 | 入队时检查通过，稍后执行就不必再考虑变化 |

这五类检查可能发生在不同组件中。阅读架构图时，可以逐项寻找负责作出决定的组件，以及作出决定后真正执行它的组件。把一个组件命名为“安全网关”，本身不能回答这些问题。

## 委托身份：Token Exchange 提供了什么

OAuth 2.0 Token Exchange 定义了向授权服务器交换安全令牌的协议，可以表达代理其他主体行动的关系。`subject_token` 和 `actor_token` 分别提供被代表主体与代理方的信息；是否签发复合令牌、签发什么权限，由授权服务器及其策略决定。[RFC 8693 §1.1](https://www.rfc-editor.org/rfc/rfc8693.html#section-1.1)

在 JWT 中，最外层 `act` 标识当前代理，嵌套 `act` 可保留之前的代理。规范要求访问控制考虑令牌顶层声明和当前代理，历史代理仅作信息记录。因此，委托历史不能被理解成把沿途所有人的权限合并起来。[RFC 8693 §4.1](https://www.rfc-editor.org/rfc/rfc8693.html#section-4.1)

一个便于理解的例子是：服务甲代表员工请求服务乙。我们至少需要区分“员工是谁”和“当前真正发请求的是谁”。否则，后续调查只能看到一个员工账号，难以区分员工直接操作与软件代为操作。

## 持钥证明：DPoP 的边界在哪里

DPoP 将 OAuth token 与客户端密钥绑定，请求附带签名证明。证明中的 `htm` 对应 HTTP 方法；`htu` 对应目标 URI，但排除 query 和 fragment。它不保证请求正文及一般请求头的完整性；传输保护和业务授权仍需各自完成。[RFC 9449 §4.2](https://www.rfc-editor.org/rfc/rfc9449.html#section-4.2)、[§11.7](https://www.rfc-editor.org/rfc/rfc9449.html#section-11.7)

据此可以构造一个检查题：同一个合法客户端发出两次 `POST /exports`，第一份正文要求导出公开文档，第二份正文要求导出人事档案。即使两次都附带合法的持钥证明，是否准许第二次导出，仍取决于服务对文档、租户和导出目的地的检查。持钥证明不能代替这项业务决定。

## 权限范围：短期凭证还需要限制目标

OAuth 安全最佳实践建议把访问令牌权限限制到具体用途所需的最小范围，并建议将其受众限制到一个或少量资源服务器；资源服务器需要检查令牌是否发给自己。[RFC 9700 §2.3](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.3)

可以分别想象两种配置：一张能在所有系统使用、五分钟后过期的凭证；另一张仅能读取某个项目文档、同样五分钟后过期的凭证。两者寿命相同，可触及的对象却不同。审查权限时，应分别列出时间范围、对象范围和操作范围，避免用“已经很短期”解释其他范围为何过宽。

## MCP 授权与业务权限

MCP 的授权规范包含 scope 选择和运行中的增量授权流程。服务器可以用挑战响应说明当前操作所需的 scope，客户端据此发起授权；规范也建议限制重试，避免同一资源与操作反复升级失败。[MCP Authorization，2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

阅读这一机制时，可以把“服务器声称需要哪些 scope”视作完成请求的技术条件。系统是否允许当前任务获得这些 scope，还需要一个独立的策略决定。一个导出文档的任务遇到要求增加删除权限的挑战，不能只因为协议提供了授权流程，就推断删除权限合理。

## 如何带着这些背景阅读原文

第一遍追踪身份和权限从哪里来，第二遍追踪敏感数据与输出之间的路径。最后检查一个更具体的问题：如果授权后发生延迟、重试、参数变化或缓存复用，最初作出的决定是否仍然适用？[阅读笔记](notes.md)用这些情形展开讨论。
