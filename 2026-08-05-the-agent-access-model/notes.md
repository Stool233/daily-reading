# 阅读笔记与讨论：智能体访问模型

>
> 更新：2026-09-13。

原文观点集中概括在[中文导读](translation.zh.md)。以下是阅读后自行构造的分析、反例和讨论建议，不代表作者已经实现或证明了这些设计，也不代表用户已经形成的个人结论。

## 1. 用请求对象检查授权是否足够具体

设想一个文档导出工具，接受以下请求：

```json
{
  "operation": "export_document",
  "document": "design-42",
  "tenant": "team-a",
  "format": "pdf",
  "destination": "internal-review"
}
```

假设审批只检查了 `operation`，却没有检查 `document` 和 `destination`，那么允许的是一类非常宽的行为。同一个工具名可以代表导出不同文件、发给不同对象。讨论授权粒度时，应把这些参数视作决策输入。

另一个问题发生在检查之后：如果队列保存的是可变对象引用，排队期间有人改了 `destination`，执行器拿到的请求就可能与审批时不同。我们可以要求审计记录关联到一份规范化后的请求表示，并检查执行器使用的内容是否一致。请求摘要适合帮助比对，但摘要本身不会阻止错误执行；真正的约束仍要落实在执行路径中。

这也解释了为何[导读中的 DPoP 背景](translation.zh.md)必须与参数授权一起读：合法身份发出的请求，仍然可能要求一个没有被授权的业务动作。

## 2. 对权限变更做一次并发反例推演

下面是一个假设系统的错误执行，不是实际产品漏洞报告。

| 时刻 | 模型与工具层 | 网络执行点 |
| --- | --- | --- |
| t0 | 尚未把受保护内容交给模型 | 缓存着策略版本 6 的外发许可 |
| t1 | 控制面写入版本 7，工具层收到更新 | 更新消息延迟，仍使用版本 6 |
| t2 | 系统仅凭控制面写入成功就交付内容 | 仍未切换策略 |
| t3 | 模型构造了包含该内容的新发送请求 | 错误地按旧许可放行 |

这个反例区分了三件事：策略已经保存、策略已经传播、所有相关动作已经受新策略约束。只观察第一件事，无法推出后两件事。

可以用一个自定义不变量描述我们期望的性质：

```text
向模型交付数据 d
  ⇒ 每条可能携带 d 的受控输出路径，都已经满足 d 所要求的限制
```

这个表达仍需要实施者明确“可能携带”“受控路径”和“满足限制”的含义。比如一条已经建立的连接是否可以继续发送，或者某个远端工具是否会自己调用另一个服务，不能靠本地状态变量的名字决定。

推演时还应检查系统如何处理中间失败：更新消息重发是否幂等，进程重启会不会读回旧许可，执行点失联是否被误当成已经撤销。每一种情形都可以写出时间线，寻找数据已可见而限制尚未生效的间隙。

## 3. 只允许数字输出，是否已经足够

构造一个只返回总数的工具。第一次查询六人的费用总额，返回 12,000；第二次排除其中一人，返回 9,900。两次合法输出相减，就得到该人的费用 2,100。

这个例子不需要自由文本字段，也不需要把文件整体发送出去。问题在于两次回答组合后透露了更多信息。固定输出结构能够减少表达范围，但输出之间仍可能存在可利用的关系。

由此得到的讨论建议是：分别评估单次响应、可选查询范围和同一接收方累计得到的回答。最小分组人数、禁止过度重叠的查询、查询预算等都只是待评估的设计选项；是否有效，要根据允许的查询族与攻击者已有信息分析，不能只看到某个限制就宣称具有完整隐私保证。

## 4. 共享缓存需要保持哪些条件

设想同一句问题先由项目负责人提出，稍后由外部协作者提出。若缓存键只有问题文本，服务可能直接把第一次生成的答案交给第二个人。这时，节省一次检索和推理，也跳过了本来应当重新成立的访问条件。

一种可供讨论的缓存设计，是记录产生答案时使用的数据版本、租户、授权上下文和来源集合，并在复用时重新判断当前接收方是否仍满足条件。这不是完整方案：权限可能在缓存写入后被撤销；生成答案也可能混合多份来源，无法简单归属于单个文档。

因此，需要进一步区分两个问题：系统能否判断当前用户可以读取哪些原始材料；系统能否判断一个已经生成的答案包含哪些受限信息。前者成功，并不自动给出后者的答案。

## 5. 把剩余问题讨论到可作决定的程度

| 讨论点 | 初步判断 | 还需要哪些证据 |
| --- | --- | --- |
| 两个系统给同一数据不同分类 | 先找出分类责任和版本来源，再讨论自动合并规则 | 分类依据、变更记录、误标样本 |
| 正常任务频繁遇到拒绝 | 按失败原因区分任务设计、资源范围和执行故障 | 成功路径、被拒绝的具体动作、是否存在权限更小的替代路径 |
| 长任务被拆开后难以继续 | 检查任务间必须传递什么，并明确这些输入带来的约束 | 传递字段、持久化位置、接收任务的初始条件 |
| 希望依靠人工审批解决异常 | 审批应让人看懂具体对象、接收方与有效期 | 实际审批内容、变更前后的请求、审批和执行的关联记录 |
| 日志显示请求被允许，却不知道是否成功 | 授权决定、执行尝试和实际效果需要分别记录 | 资源侧响应、失败重试、关联标识及其覆盖范围 |

这里的目标是让讨论从“权限太严”或“权限不够严”，推进到可定位的对象、时间点和失败条件。

## 6. 本轮阅读形成的判断

我更愿意用具体的失败时间线评价这类访问架构：选一个授权决定，再沿着队列、缓存、网络和下游服务追踪它，观察后续哪些条件可能变化。这样可以检验一个局部正确的决定，是否在真实执行过程中仍然有效。

另一项值得持续追问的取舍，是系统为了获得可检查的边界，愿意牺牲多少任务连续性和共享上下文。这个代价需要用工作负载衡量；单凭架构图，既不能断言它过于保守，也不能断言它已覆盖所有数据流。
