# 阅读笔记

## 一句话总结

Agent swarm 的规模收益主要来自上下文隔离和组织设计；真正有效的模型路由不是“简单活给便宜模型”，而是让高质量规划减少整个 worker 集群的搜索、冲突和返工。

## 关键概念

- **任务树即上下文架构**：planner 保留祖先目标，worker 只处理叶节点，避免单个上下文同时承载全局与全部细节。
- **协调面（coordination plane）**：VCS、设计文档、编译引用、合并代理和文件拆分策略共同构成群体协调基础设施。
- **低相关审查**：可靠性来自多个盲点不同的 reviewer，而不是寻找一个完美 reviewer。
- **环境记忆**：Field Guide 让 agent 通过外部 artifact 把意外经验传给后继者。
- **组织熵**：无效提交、冲突、重复 package 和超大文件比提交数更能反映蜂群是否失控。
- **下游成本乘数**：planner 的质量影响每个 worker 的 token、返工和冲突，因此规划成本应按全局效果计算。
- **概率编译器**：swarm 把意图逐层降低为实现，但每一步都可能损失语义。

## 最值得记住的数据

| 观察项 | 旧 harness | 新 harness |
| --- | ---: | ---: |
| Grok 运行的合并冲突 | 暂停前超过 70,000 | 完整四小时少于 1,000 |
| 最热门文件的冲突 | 7,771，涉及 1,173 个 agent | 全库最高 47 |
| Rust crate 数 | 54 | 9 |
| Fable 配置引擎代码 | 64,305 行，最终 100% | 9,908 行，最终 100% |
| Opus 配置引擎代码 | 19,013 行，97% | 4,645 行，100% |

模型组合的总成本从 Opus 4.8 + Composer 2.5 的 1,339 美元，到全程 GPT-5.5 的 10,565 美元。Worker 在每次运行中至少承担 69% 的 token，大多数运行超过 90%。

## 我的理解

这篇文章最有价值的地方，不是证明“更多 agent 更强”，而是把失败从模型能力问题重新描述为组织问题。旧系统并不缺行动力：68,000 次提交说明它极其活跃；它缺的是决定权边界、共享事实、冲突仲裁和结构性负反馈。没有这些机制，算力只会更快地制造组织熵。

任务树也不只是调度结构，而是一种上下文压缩。Planner 不实现、worker 不规划，等于用角色边界替代一部分上下文窗口。这个解释比“并行带来加速”更强，因为它说明即使不追求极端并发，角色拆分仍可能改善中等任务。

模型经济学部分尤其值得警惕一个常见误区：按单次调用价格做路由。一个便宜 planner 如果留下模糊或错误的计划，可能让数百个 worker 重复探索；一个昂贵 planner 如果能一次消除关键不确定性，反而降低总成本。路由器需要优化端到端任务成本，而不是局部 token 单价。

## 证据的强处

- 新旧 harness 使用相同模型与时间预算，能较好隔离 harness 变化。
- 结果不只看最终测试分数，还观察冲突、提交速率、热点文件、package 数和代码规模。
- 隐藏测试套件减少 agent 针对评分器直接优化的机会。
- 人工检查作弊和不均衡实现，为纯 benchmark 分数补了一层约束。
- 同时比较全前沿模型和 planner/worker 混合配置，能够观察成本如何沿任务树传播。

## 仍需谨慎的地方

- 当前证据集中在从文档重建 SQLite；任务是否能干净地树状拆分，会影响方法能否迁移。
- 文章尚未完成 planner × worker 的完整组合矩阵，也没有给出重复运行的方差。
- `sqllogictest` 很强，但通过测试不等于实现已具备 SQLite 的完整兼容性、安全性和可维护性。
- 多数机制是一起进入新版 harness 的，现有结果难以判断每项机制各自贡献多少。
- 自定义 VCS 是系统核心，却也让方案的复现门槛和基础设施成本显著提高。
- 低相关 reviewer 的关键是错误独立性；更换提示或“个性”不一定真的消除共享模型和共享证据造成的相关盲点。
- 任务树对横切依赖、全局不变量和强耦合模块未必自然，实际结构可能更接近 DAG。

## 与 Specula 文章的共同主线

Cursor 的结尾说，swarm 时代最稀缺的是“对意图的准确描述”；Murat Demirbas 对 Specula 的核心追问则是：如果规格从可能有 bug 的代码和 issue 中反推，权威意图到底在哪里？两篇放在一起，结论比任何一篇单独阅读都更清楚：生成和执行可以被大规模扩展，但系统不能凭空制造可信意图。

SQLite 实验有一个独立于 swarm 的隐藏测试集，因而至少提供了较难被直接改写的外部评价信号。Specula 的很多不变量和模型来自同一批代码 artifact，容易形成循环。两者的差别提示我们：反馈器越独立于被优化对象，越能抑制 reward hacking 和群体共同盲点。

Cursor 的多视角审查与 Specula 的“trace validation + model checking”也有相同结构：让不同反馈力相互校正。但“不同”不能只停留在工具名字上；如果它们最终都继承同一个错误意图，叠加再多也只能得到一致的错误。

## 对 agent 工程的启发

- 先定义设计决策的唯一所有者，再拆实现任务；不要让两个子树独立决定同一件事。
- 把设计文档做成可被代码或检查器引用的 artifact，让决策变更能够自动传播。
- 用冲突率、返工率、热点集中度和重复结构衡量 swarm，而不是把提交数当生产率。
- 把合并、拆大文件和全局重构交给专门角色，避免要求局部 worker 临时吸收全局上下文。
- 共享记忆要有预算、可编辑和淘汰机制；“把所有经验都注入”会重新制造上下文问题。
- 评估模型路由时，记录 planner 决策对下游 token 和失败率的影响。
- 为规格建立独立验收信号；否则概率编译器只能检查自己是否忠实于自己生成的中间表示。

## 可延伸思考

- 任务图什么时候必须从树升级为 DAG？跨子树依赖应由 planner、协调器还是类型系统表达？
- 如何量化 reviewer 之间的错误相关性，而不是只观察它们给出不同措辞？
- Field Guide 如何判断一条经验已经过时，或只适用于某个模型和 harness 版本？
- 自定义 VCS 中哪些机制可以回迁到普通 Git 工作流，服务几十个而非几百个 agent？
- Planner 的奖励是否应该直接包含 worker 总 token、冲突数和返工深度？
- “规格即提示”之后，规格本身应由谁审查，又由什么外部事实约束？

## 待补充问题

- 每种模型组合运行了多少次，分数与成本方差如何？
- 新 harness 中各机制的消融实验结果如何？
- 测试达到 100% 后，SQLite 实现的崩溃安全、事务语义、性能和安全审计结果如何？
- Field Guide 的行数预算、更新冲突和垃圾回收策略是什么？
- 每秒 1,000 次提交的 VCS 如何表示原子性、分支、回滚和可审计历史？
