## 从“让更多 agent 并行”转向“有意识地设计组织”

Cursor 早先曾让一个长时间运行的 agent swarm 从零构建 Web 浏览器。那个实验证明了很多 agent 可以共同完成大任务，但成品距离成熟软件很远。早期方法更像经验式爬坡：先让系统跑起来，再根据失败不断加规则。

这次他们重新挑战一个旧蜂群做不好的任务：不看 SQLite 源码，只根据 835 页文档，用 Rust 从零实现 SQLite。新旧蜂群使用相同模型和相同时间预算，再用未向 agent 暴露的 SQL 测试集衡量结果。新版在每一种模型组合上都更好，这使 Cursor 把问题从“并行多少 agent”转向“怎样有意识地设计 agent 的分工、通信和反馈环境”。

## 任务树首先是一种上下文管理机制

大型目标天然可以递归拆成树：根节点是总体目标，内部节点是子问题，叶节点是可直接执行的工作单元。Cursor 的蜂群据此设置两类角色：

- planner 使用最强模型，保留全局视图，负责设计决策、任务拆解和委派；
- worker 通常使用更快、更便宜的模型，只负责某个局部任务的实现。

单个 agent 独自处理长任务时，必须同时记住祖先目标、当前路径和叶节点细节。它要么专注眼前工作而丢失全局，要么维护全局却降低局部执行质量。角色分离后，planner 的上下文不会被底层代码淹没，worker 也不必为整体规划消耗窗口。

因此，文章认为 swarm 的可扩展性主要来自上下文效率，而不是并行本身。即使任务不大，把“维持全局”和“完成局部”分开，也可能改善表现。这里的组织形式与科斯对企业层级的解释相似：协调成本增长得比工作本身更快，于是系统会形成边界清楚的层级，而不是让所有成员彼此直接沟通。

## 为什么 Git 不足以承载每秒千次提交

早期浏览器 swarm 在 Git 上的峰值大约是每小时 1,000 次提交，新系统则达到约每秒 1,000 次。Cursor 为此从零构建 VCS。吞吐量只是原因之一；更重要的是，每次变更都经过版本控制层，所以冲突最先在这里出现，协调机制也能在这里被强制执行。

文章列出五类在 agent 速度下被放大的失败模式。

### 脑裂设计

两个 planner 不知道彼此的工作，在代码库不同位置为同一概念做出不同实现。解决方式是让 planner 自己保留设计决策，不把它们下放给 worker；同时要求任务树之间不能重复决定同一个问题。

### Planner 之间的争用

更麻烦的情况是两个 planner 知道彼此，却对同一批文件反复改写。普通合并工具只能合并文本，无法协调两套现实认知。新版把决策记录到共享设计文档，依赖决策的代码带有可由编译器检查的引用。协调器先合并矛盾的设计文档，再让引用把结果传播到下游代码。

### 合并冲突

Worker 遇到冲突时需要暂停自己的工作、吸收另一方上下文并重新合并，但它们往往会覆盖对方或放弃自己。Cursor 改为派一个中立的第三方 agent 代表双方解决冲突，作用类似高速运行的 merge queue。

### 超大文件

热门文件会被许多 agent 各加一点代码，却没有谁对整体尺寸负责，最后在传输、diff 和合并时成为瓶颈。Worker 可以标记膨胀文件；文件被标记后暂停新提交，再由外部 agent 将其拆成更小模块。

### 架构僵化

在有人类参与的代码库里训练出的 agent 往往学会避免触碰核心代码，即使核心设计确实应该改变。新版允许有意引入范围明确的破坏性变更，并留下原因。编译错误会把这个决策传播到所有依赖旧设计的地方，相关 agent 读到说明后更新自己负责的部分。

## 用低相关的审查视角叠加可靠性

长时间、多 agent 的系统会持续积累小错误。Cursor 尝试给 reviewer 不同的信息：完整 worker 对话、只有产出、只有代码库；也尝试不同模型、训练和行为风格。没有单一视角能发现全部问题，但彼此低相关的 reviewer 可以叠加。审查通常比重新完成工作便宜，因此把更多算力投入审查具有较高回报。

这里的重点不是简单增加 reviewer 数量，而是降低共同盲点。如果所有 reviewer 看同样的证据、采用同样的模型和提示，它们很可能一起漏掉同一类错误。

## Field Guide：让环境替 agent 保存组织记忆

Cursor 用“迹象引导”（stigmergy）解释另一项设计：群居生物通过改变环境来间接协作，环境再影响后来的个体。Agent 也可以把意外经验写给未来的自己和队友。

Field Guide 是完全由 agent 管理的目录，其 `index.md` 会在每个 agent 启动时自动注入上下文。Agent 自己决定记录什么，唯一硬约束是行数预算。因为模型权重不随一次运行改变，最值得保存的是出乎意料、能缩短下一次轨迹的信息。行数预算则迫使群体持续筛选，而不是无限堆积上下文。

## SQLite 实验怎样衡量结果

新版蜂群拿到完整 SQLite 手册，但拿不到 SQLite 源码、二进制、测试套件，也不能访问互联网。外部评分使用 SQLite 项目的 `sqllogictest`，其中有数百万个已知答案的查询。Agent 事先不知道这套测试存在。Cursor 还对每次运行进行人工检查，确认没有作弊、走捷径，或只针对容易得分的区域实现。

受测配置包括：

1. GPT-5.5 同时担任 planner 和 worker；
2. Grok 4.5 同时担任 planner 和 worker；
3. Opus 4.8 规划，Composer 2.5 执行；
4. Fable 5 规划，Composer 2.5 执行。

四小时截止时，新版各配置位于 73% 到 85%，旧版位于 11% 到 77%。旧版 Grok 在两小时前因失控被暂停；新版所有配置后来都通过了 100% 的测试。文章没有把某一时刻的分数当成全部结论，因为不同 swarm 会选择先打基础或先深入局部，曲线形状并不相同。

## 高活动量可能只是无效忙碌

Grok 4.5 的旧版运行在不到两小时内产生 68,000 次提交，速度大约是新版的 70 倍。单看提交数，它似乎更“高产”；但旧版在暂停前已经积累超过 70,000 次合并冲突，而且冲突仍在加速。新版完整四小时的冲突少于 1,000 次。

旧版最热门的文件发生 7,771 次冲突，被 1,173 个 agent 修改；新版全库最热门文件只有 47 次冲突。旧版膨胀到 54 个 Rust crate，其中出现三个独立 SQL 包；新版很早稳定在 9 个 crate。数据说明，高频提交可以代表 thrash、争抢和反复推翻，而不是有效产出。

最终代码规模也揭示了结构质量。Fable 混合配置中，新旧系统都通过完整测试，但旧版需要 64,305 行引擎代码，新版只需 9,908 行。Opus 混合配置里，旧版以 19,013 行达到 97%，新版以 4,645 行达到 100%。Harness 的价值不只是提高测试分数，还在于减少重复实现和组织熵。

## 新的模型经济学：规划质量会放大到所有 worker

各模型组合得到的质量大致相近，成本却从 Opus 4.8 + Composer 2.5 的 1,339 美元，到全程 GPT-5.5 的 10,565 美元。每次运行中，worker 至少消耗 69% 的 token，大多数时候超过 90%。

大型任务真正需要前沿判断力的时刻并不多，主要是最初拆解、架构决定和困难权衡。一旦强 planner 把不确定性压缩成详细指令，便宜模型就可以完成大部分执行。全程 GPT-5.5 的运行里，worker 单独花费 9,373 美元；Opus 规划、Composer 执行时，整个 worker 集群只花 411 美元。

但 planner 的账单不能孤立看待。Fable 的单 token 价格约为 Opus 的两倍，却因为规划 token 少而产生略低的 planner 账单；然而它留下的工作让 worker 消耗数倍 token，导致总成本明显更高。一个规划 token 的价值，应该按它减少了多少下游搜索、返工和冲突来评估。

## 从代码补全到“规格即提示”

文章最后把 AI 编程的抽象层级串起来：自动补全让工程师以代码行为单位工作，早期模型提高到代码块，agent 提高到文件或功能，swarm 则把工作单位提高到规格说明。

在 SQLite 实验中，人给出 835 页意图描述，系统返回数据库。Cursor 因此判断，未来稀缺的不是生成代码的 token，而是对意图的准确表达。

Swarm 像一台概率编译器：planner 把目标解析成任务树，再逐层降低为可执行工作。传统编译器每一步都应保留语义，而 swarm 每一步都有概率偏离。VCS、设计文档、review lens、Field Guide、测试和角色分工，都是在缩小这条语义鸿沟。

## 需要保留的限定

文章展示的是 SQLite 这一大型任务上的若干模型组合，还没有完成 planner × worker 的完整矩阵。测试通过能证明较强的行为兼容性，却不能自动等同于 SQLite 的完整语义、安全性、可维护性或生产成熟度；作者也明确说，对公开产物尚未做深入人工分析。

成本数字同样依赖当时的模型价格、提示、运行时和任务结构。可以迁移的不是某个固定美元数，而是两个结构性结论：worker 是 token 大户；planner 质量会通过整个任务树产生乘数效应。

## 术语对照

- **Agent swarm**：智能体蜂群 / agent 蜂群
- **Planner**：规划智能体
- **Worker**：执行智能体
- **Harness**：围绕模型的运行、协调与反馈系统
- **Split-brain design**：脑裂设计
- **Contention**：争用
- **Megafile**：超大文件 / 巨型文件
- **Ossification**：僵化
- **Review lens**：审查视角
- **Stigmergy**：迹象引导，通过改变环境进行间接协调
- **Field Guide**：由 agent 自主管理的共享经验指南
- **Specs as prompts**：把规格说明作为提示和工作入口
