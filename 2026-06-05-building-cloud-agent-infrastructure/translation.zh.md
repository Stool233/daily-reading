## 桌面 agent 的默认世界

文章从一个对比开始：今天许多 agent 框架默认自己活在桌面环境里。一个用户，一台机器，一个进程。Agent 在笔记本打开时运行，写本地文件，把 API key 放在环境变量里；运行失败了，用户就在旁边重试；缺包了，直接往用户的 Python 环境里安装。

这些默认条件在桌面上看起来很自然，因为状态、密钥、网络和生命周期都落在同一个可信边界内：用户的机器。

云端 agent 没有这些便利。它运行在一次性 sandbox 里，底层硬件可能和陌生用户共享，触发者可能不是眼前的人，而是定时任务、HTTP 请求或另一个 agent。用户经常不在场。Sandbox 里的代码可能已经被恶意输入影响。文件系统要跨部署保留，凭证不能和 agent 放在一起，重试和生命周期也不能靠人手补救。

这就是文章的核心前提：把桌面 agent 搬到云上，不是换一台服务器那么简单，而是换了一整套信任模型和生命周期模型。

## 经验一：拆开变化慢的状态和变化快的代码

第一条经验是区分变化节奏。桌面环境里，用户环境和 agent runtime 往往是同一个东西。但在云端，二者应该由不同所有者控制，并按不同节奏变化。

用户环境变化慢。比如一个股票分析 agent 可能安装了 matplotlib，下载了市场数据，写了图表脚本。这些东西构成了 agent 的“肌肉记忆”。CREAO 的做法是把用户满意的环境冻结成 sandbox snapshot。之后每次运行都从同一个镜像启动，包、文件和版本都保持一致。

平台 runner 变化快。Runner 是平台维护的那层小型 harness library，负责每次运行时管理 agent。平台团队可能一天部署很多次。问题在于，如果用户环境和 runner code 被打包到同一个 snapshot 里，就会出现冲突：用户希望环境不动，平台希望 runner 经常更新。

文章提到他们最初的处理方式比较粗暴：如果启动时发现 snapshot 里的 runner 版本不是最新，就丢掉 snapshot，从干净模板重新启动。这个办法在交互式场景里没有立刻暴露问题，因为影响只发生在部署后的第一次运行。

但无人值守运行让问题变得严重。一个周一早上九点的 cron job，不应该因为平台八点五十五分部署而失去用户环境。用户期望的是：环境冻结到他自己改为止。

最后的方案借鉴了操作系统边界：内核可以升级，用户 home directory 不该被擦掉。对应到 agent 平台，就是从用户冻结的 snapshot 启动，保持用户环境不动，然后只热替换 runner。

这个热替换流程大致包括：先在 sandbox 内临时位置准备新 runner，做语法或加载前检查；确认没问题后再原子替换旧 runner；清理可能导致旧字节码继续运行的缓存；如果任何步骤失败，就终止该 sandbox 并重试，避免半升级状态继续执行任务。成功运行后，如果 runner 被替换，再重新 snapshot，把新 runner 烘进用户镜像，下一次就不需要重复替换。

这条经验背后的诊断问题很值得记：一个需要持久化的 artifact，到底由谁控制变化节奏？如果用户和平台共同拥有同一个 artifact，但变化节奏相反，系统迟早会为这种耦合付费。

## 经验二：让密钥留在执行边界之外

第二条经验是安全边界。桌面 agent 通常以用户身份在用户机器上运行，使用用户的 key，访问用户的网络。云端 agent 完全不同：它在共享基础设施上运行，面向开放互联网，执行的代码可能由 LLM 根据恶意 prompt 写出。

文章给出的规则非常清楚：长期凭证永远不进入 sandbox。Sandbox 里不应该有 OAuth token、API key 或其他可复用密钥，不应该放在环境变量、文件或内存里。

当 agent 需要调用 Slack、GitHub 或用户自己的 API 时，它不直接持有 token，而是向 sandbox 外部的 API bridge 发起本地请求。Bridge 在宿主侧附加用户凭证并转发请求，再把响应返回给 sandbox。这样，凭证从头到尾都没有进入 sandbox。

关键问题是 bridge 如何判断 sandbox 有权请求。文章采用两层检查。

第一层是网络边界。Bridge 只接受来自 sandbox 主机内部网段的连接，来自开发者笔记本、泄露 URL 或公网的请求会先在网络层被挡掉。

第二层是每次运行签发的短期 JWT。Sandbox 启动时，平台签发一个只对当前 user、app、session 有效的 token，并设置覆盖运行窗口的过期时间。Sandbox 每次调用 bridge 都必须携带它。Bridge 验签、检查过期时间，再决定是否解析用户保存的凭证并在服务端附加。

这样即使 sandbox 被劫持，攻击者拿到的也只是一个短期、窄作用域、还受网络边界限制的能力，而不是可长期复用的主密钥。

文章还提到，同一个 bridge 也承载计费扣减、日志和 metrics。也就是说，sandbox 与平台之间只有一个受控跨界接口。Sandbox 内部默认不可信，真正的可信逻辑留在边界之外。

## 底层模式

文章最后把云端 agent 基础设施总结成几条性质。

第一，用户状态留在 sandbox snapshot 中，直到用户自己改变它。第二，平台代码可以独立于用户状态热更新。第三，凭证留在宿主侧，不进入 agent 执行环境。第四，所有触发方式共享同一条执行管线。

最后一条尤其关键。无论是用户点击运行、定时任务触发，还是 API 调用或其他软件触发，都应该进入同一个 `executeAgent` 逻辑。这样计费、日志、观测、权限和重试都保持一致。新增一种触发方式只是路由变化，而不是新架构。

文章最终给出了一个很好的产品抽象：云端 agent 是一个带自然语言接口的函数。它的实现属于用户；它的触发面、运行时和安全边界属于平台。

这句话也解释了为什么云端 agent 值得构建。桌面 agent 绑定在一台机器上，云端 agent 则可以被整个软件系统调用。平台的责任，是让它在部署之间存活，在共享硬件上安全运行，并接受用户起初没有预料到的调用者。

## 术语对照

- **Cloud agent infrastructure**：云端 agent 基础设施
- **Desktop agent framework**：桌面 agent 框架
- **Sandbox**：沙箱 / 隔离执行环境
- **Runner**：运行器 / 平台侧 harness 代码
- **Sandbox snapshot**：沙箱快照
- **Hot-swap**：热替换
- **Execution boundary**：执行边界
- **API bridge**：API 桥接层
- **IP allowlist**：IP 允许列表
- **Short-lived JWT**：短期 JWT
- **Trigger surface**：触发面

## 核心脉络

1. 桌面 agent 默认的可信边界、生命周期和状态模型，在云端都不成立。
2. 云端 agent 必须把持久状态、平台 runner、凭证、触发入口和观测路径显式建模。
3. 用户环境变化慢，平台 runner 变化快；把它们放在同一个 artifact 里会制造部署和无人值守运行的冲突。
4. 长期凭证不能进入 sandbox，应该通过宿主侧 bridge、网络边界和短期 token 控制访问。
5. 所有触发方式共享同一执行管线，才能让计费、日志、metrics 和安全策略保持一致。
6. 云端 agent 的本质是“带自然语言接口的函数”：用户拥有实现，平台拥有运行时和边界。
