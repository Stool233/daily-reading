# 阅读笔记

## 一句话总结

云端 agent 不是桌面 agent 的远程版本，而是一个必须显式重建状态、代码更新、密钥、触发、计费和观测边界的执行平台。

## 关键概念

- **变化节奏**：用户环境变化慢，平台 runner 变化快；两者不应绑定在同一个不可分 artifact 里。
- **冻结快照**：把用户满意的环境保存成稳定 snapshot，保证无人值守运行的可复现性。
- **Runner 热替换**：在保持用户环境不变的前提下更新平台侧运行代码。
- **执行边界**：sandbox 内部默认不可信，长期凭证和关键平台逻辑必须留在边界之外。
- **API bridge**：宿主侧受控接口，负责附加凭证、输出日志、处理计费和 metrics。
- **短期 per-run capability**：每次运行签发窄作用域 token，降低 sandbox 泄露后的损害范围。
- **统一执行管线**：UI、cron、API 和软件触发都走同一套运行、计费、日志和安全流程。

## 文章主张

1. 桌面 agent 默认用户在线、机器可信、状态本地、失败可人工重试；云端 agent 不能依赖这些条件。
2. 用户状态和平台 runner 的所有权不同，更新节奏也不同，需要拆成两个层。
3. 用 snapshot 保持用户环境可复现，用热替换更新 runner，避免平台部署破坏用户状态。
4. 长期凭证永远不应进入 sandbox，所有认证请求都应通过宿主侧 bridge。
5. Bridge 需要同时依赖网络边界和短期 token，而不是只靠一个秘密字符串。
6. 云端 agent 的价值在于它可以被整个软件系统调用，而不只是绑定在用户笔记本上。

## 值得记住的工程点

- 桌面框架里自然成立的东西，在云端都要变成平台保证：持久化、身份、网络信任、重试和生命周期。
- 如果 runner 和用户环境打包在同一个 snapshot 中，平台部署会和用户可复现性冲突。
- 热替换 runner 前要先验证新代码，失败时宁可丢弃 sandbox，也不要让半升级状态继续执行。
- 清理运行时缓存是更新流程的一部分，否则可能换了文件却还执行旧缓存。
- API bridge 最好成为 sandbox 与平台之间唯一的受控跨界接口。
- 新触发方式如果复用同一执行管线，就不会复制计费、日志、安全和观测逻辑。

## 我的理解

这篇文章的核心不是“云端要更安全”这么笼统，而是把安全和可复现性都落到了 artifact ownership 上。谁拥有这个东西？谁决定它什么时候变？它在失败时如何恢复？它能不能跨部署保持承诺？这些问题如果不拆清楚，agent 平台会在无人值守场景里暴露出非常具体的 bug。

Runner 和用户环境的拆分尤其漂亮。用户环境像长期状态，平台 runner 像系统代码。把它们冻结在同一个镜像里，短期很省事，长期一定会卡在“更新平台代码”和“保护用户状态”的冲突里。文章给出的 OS 类比很好：更新内核不应该擦掉用户 home directory。

密钥设计也很务实。很多 agent demo 会把 token 直接塞进环境变量，但云端 sandbox 的威胁模型完全不同。只要假设 sandbox 内部可能被 prompt injection 或恶意代码攻破，长期凭证就必须留在宿主侧。Sandbox 能拿到的只能是短期、窄作用域、受网络边界限制的 capability。

## 与 #7 的呼应

#7 从理论上说 harness 是模型之外的运行系统；这篇则展示了 harness 在云端产品里的具体边界。状态、runner、凭证、触发入口、日志和计费，都是 harness 的一部分。它们看起来不像“AI 能力”，但它们决定 agent 能否变成可靠产品。

两篇合起来读，会得到一个很清楚的判断：agent 平台的竞争力不只来自模型，也来自谁能把执行边界、状态生命周期和反馈管线设计得更稳定。

## 对 agent 工程的启发

- 设计 agent 平台时，先画出所有权边界：用户状态、平台代码、凭证、日志、计费、触发入口分别归谁控制。
- 不要默认 sandbox 可信；把它看成可能已经被恶意代码控制的环境。
- 凭证访问应该通过能力化、短期化和宿主侧代理来完成。
- 触发入口要尽早统一，否则后续会复制出多套计费、观测和安全逻辑。
- 平台升级必须保持用户对环境可复现性的承诺，尤其是无人值守任务。
- “谁控制变化节奏”可以作为审查持久化 artifact 的通用问题。

## 可延伸思考

- Runner 热替换的不可变边界应该如何审计？
- Sandbox 内代码是否应该能观察到 runner 版本和平台变更？
- API bridge 如果成为唯一跨界接口，如何避免它变成过大的单点复杂度？
- Per-run token 的作用域应该如何表达：按用户、app、session、工具、资源，还是具体 API 方法？
- 如果 agent 之间互相触发，如何避免调用链中的权限扩大？

## 待补充问题

- CREAO 的 snapshot 如何处理用户数据迁移、依赖漏洞修复和长期镜像膨胀？
- Runner 热替换失败后的重试策略如何避免重复计费或重复副作用？
- Bridge 里的 billing、logs、metrics 与用户 API 请求是否应该拆成不同 capability？
- 对企业部署来说，IP allowlist 是否足够，还是需要更强的 workload identity？
