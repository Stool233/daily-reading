原文观点见[中文导读](translation.zh.md)。以下讨论围绕程序优化展开，其中公式、代码、假设数据和判断为自编；补充研究单独注明来源，不将其当作文章团队已经采用的方法。

## 1. 契约需要写到什么程度

以数组归约为例，仅写“把所有元素相加”，仍留下许多问题：

| 契约维度 | 需要作出的决定 | 可能影响的优化 |
| --- | --- | --- |
| 输入域 | 长度是否固定，是否允许空数组 | 展开循环、边界处理 |
| 数值类型 | 整数、定宽整数或浮点数 | 溢出、舍入与向量指令 |
| 结果关系 | 精确相等，还是某种误差界 | 并行归约、运算重排 |
| 存储条件 | 输入输出是否可能共享内存 | 原地更新、读写重排 |
| 异常输入 | 如何处理 NaN、无穷值等 | 分支简化、特殊值路径 |
| 可观察效果 | 是否允许修改输入，是否要求确定性 | 并发执行与缓存复用 |

这张表是用来检查规格是否足够明确，不是要求每个程序都采用同一种严格标准。允许近似计算可以是合理的工程决定；关键是优化器、验证器和调用方理解的是同一份约定。

## 2. 浮点数反例：数学恒等式需要哪些前提

下面的 Python 示例在本次阅读环境运行过：

```python
a, b, c = 1e16, -1e16, 1.0

print((a + b) + c)  # 1.0
print(a + (b + c))  # 0.0
```

第一种顺序先抵消两个大数，再加上 1。第二种顺序中，较小的 1 在与大数相加时没有保留下来。Python 文档解释了二进制浮点表示与舍入造成的这类限制。[Python 浮点数说明](https://docs.python.org/3/tutorial/floatingpoint.html)

这个自编反例使一个讨论变得具体：如果候选优化改变了归约顺序，那么它能否被接受，要依据契约规定的结果关系。仅仅说“两段代码计算同一个数学表达式”，没有回答有限精度执行是否满足要求。

例如，可以先约定如下标量误差条件：

```text
abs(candidate - reference)
    <= absolute_tolerance + relative_tolerance * abs(reference)
```

这只是一个示例条件，还需要另外规定特殊值、向量结果的比较方式，以及参考结果的精度。不同业务可能需要不同条件；不能把某一组容差当作所有内核通用的正确性定义。

## 3. “没有发现错误”可以对应不同证据

下面是对验证证据的阅读分类，不是对某个项目的测评。

| 证据 | 可以直接支持的判断 | 仍需保留的条件 |
| --- | --- | --- |
| 有限测试通过 | 在这些具体输入和环境中符合检查项 | 不能自动覆盖未测输入 |
| 针对性或随机测试未发现反例 | 在采用的生成策略和预算内没有发现反例 | 输入分布和检查项会影响发现能力 |
| 有界符号检查通过 | 在声明的模型和边界内成立 | 边界外、未建模行为仍需单独分析 |
| 在明确模型中完成证明 | 结论覆盖证明陈述及其假设 | 陈述是否对应实际机器和调用环境仍需确认 |

比如，一个验证器只检查归约结果，却不检查是否改写了输入数组，就可能漏掉调用方在意的副作用。这里的缺口是检查目标不完整，增加同一类测试输入未必能补上。

阅读验证结果时，我会要求同时看到四项信息：要证明的陈述、输入及环境假设、验证方法、最终状态。最终状态至少应区分通过、反例、超时和不支持，避免把未完成的分析算作成功。

## 4. 随机搜索与最优性：需要澄清的细节

文章用随机游走的理论直觉说明优化搜索；核对其引用的 STOKE 原始论文时，可以看到论文明确将方法称为不完备搜索，并说明它以牺牲完备性换取更大的可探索范围。[STOKE，摘要及第 1 节](https://theory.stanford.edu/~aiken/publications/papers/asplos13.pdf)

因此，本次讨论不把“随机搜索”理解成实际系统最终一定给出全局最优程序。可以分别定义三种目标：

- 在已经尝试的候选中，找到最好的一项。
- 在给定时间与算力预算内，尽可能获得有用的改善。
- 在完整候选空间中，证明不存在更好的程序。

前两项可以有很高工程价值，却没有自动满足第三项。评价一个优化系统时，应先确认它声称完成的是哪一项。

## 5. 性能改善值得多少搜索成本

用一组自编数据做数量级估算，所有数字均为假设：

| 项目 | 数值 |
| --- | --- |
| 基线每次运行 | 12 毫秒 |
| 候选每次运行 | 9 毫秒 |
| 生成、编译、验证与评测的额外总时间 | 2 小时 |
| 每次调用节省 | 3 毫秒 |

若仅比较累计运行时间，收回前期成本需要：

```text
调用次数 = 7,200 秒 / 0.003 秒 = 2,400,000 次
```

这解释了为什么同样一次优化，对高频内核和偶尔执行的脚本可能有不同价值。这个估算没有把 GPU、CPU、并行资源和人工时间折算成同一种货币成本，也没有考虑延迟改善本身的业务价值，因而不是完整投资回报模型。

还需要检查优化是否只是把成本移到了别处。例如候选内核的主体更快，但每次调用需要额外转换输入布局，那么应把这段成本纳入真正的使用路径。基线与候选使用的输入、数据精度和执行范围不同，单个数字就很难比较。

## 6. 验证器也应接受反例检验

一个讨论用的故障场景：候选实现只对长度为 256 的数组正确，而验证器恰好也只测试这个长度。如果上线时允许其他长度，通过测试的结果就不能支持上线后的输入域。

可以从这个场景提出两个不同修正：把任务契约明确限制到 256，并在入口拒绝其他长度；或者扩展实现和验证，使其覆盖实际允许的长度。两者解决的任务范围不同，不应把它们记成同一种正确性改进。

同样，若候选生成反复看到全部评测输入，应额外考虑它是否只适应了这些样本。可以留出独立评测、增加边界用例，或采用适当的符号方法。每种办法都要说明自己的覆盖范围；“增加一个检查步骤”本身不是充分论据。

## 7. 本轮阅读形成的判断

我认为评估这类系统，最有效的是拿一个实际候选，把规格、验证结果和性能结果放在一起。这样才能看清一次提速是否伴随输入域缩小、精度变化，或者测量范围变化。

后续若出现更详细的技术说明，最想核对的是：契约如何表达；验证覆盖哪些输入、数值与内存行为；失败或超时如何处理；性能结果如何复现。先把这些信息对应起来，再判断“无需逐行阅读”在多大范围内成立。
