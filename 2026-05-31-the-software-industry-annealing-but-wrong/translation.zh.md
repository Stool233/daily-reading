# 软件行业：退火，但方向错了

> 原文：[The software industry: annealing, but wrong](https://apenwarr.ca/log/20260531)  
> 作者：apenwarr  
> 发布日期：2026-05-31  
> 归档方式：中文精读摘要，不复刻完整原文译文。

## 精读摘要

作者从一个很常见的软件工程规范讲起：每个 PR 应该只改少量文件、控制在少量行数内、只做一件事、方便人类 review，并且被测试覆盖。这些原则当然有价值，尤其在成熟系统中，它们能降低回归风险，也让问题定位和回滚更容易。但作者提醒，若把所有变化都机械地压成小 PR，也会让 reviewers 承受成倍的上下文切换；所谓“质量流程”有时会变成隐藏的组织成本。

文章的核心类比是“模拟退火”。在模拟退火里，系统一开始处于高能量状态，可以在解空间里做大幅跳跃；随后能量逐渐降低，跳跃变小，系统趋于稳定。在软件里，这个类比很自然：新系统早期需要快速探索，大幅调整架构和语义；成熟系统则更适合小步、谨慎、可验证的变化。问题在于，退火式直觉会让团队天然害怕形状变化，尤其在确实需要大改的时候。

AI 辅助编码把这个问题重新摆到了台面上。LLM 可以很快生成大规模、互相关联的改动，像是在解空间里快速跳跃。它不会天然尊重团队的风险管理，也不会因为改动很大而犹豫。结果也符合直觉：这些输出可能更脆弱、更不连贯、更容易失败。但它也带来了新的能力：团队可以用很低成本探索以前不敢尝试的大方向，快速丢弃坏点子，并保留少数确实有价值的方向。

作者用 Aperture 的早期开发举例。他想实现基于金额的 LLM 使用配额，但这个功能不能只靠一个孤立模块完成。团队需要先描述哪些 session 该被附加哪些属性，需要估算不同 provider 和模型调用的价格，还要实现真正的配额执行。Grant 语法、价格近似器和配额系统彼此影响，只有一起推进，才能发现原先语义哪里不对、数据结构应该怎么改、价格信息应该如何导入。

所以作者先做了一个约 12000 行的大改，等它能端到端工作后，再拆成几个大的可 review 部分：grant、pricing、quota。重点不是说 12000 行 PR 值得鼓励，而是说真实探索无法总是按 review 顺序发生。有些改动只有先在高能量状态下成形，之后才能降温、拆分、修正和硬化。

作者随后对比了新产品 Aperture 和成熟产品 Tailscale core。新产品还在寻找形状，团队可以容忍较大的试错；成熟产品已经有多年稳定性积累和大量用户，贸然做大跳跃会带来不可接受的风险。这里的关键不是“创始人模式”或个人风格，而是产品所处阶段不同，应该选择不同的开发能量水平。

文章后半部分提出一个更普遍的判断：过度沉迷小步变化，可能让成熟产品陷入局部最优。过去大改动昂贵，所以团队自然倾向于拒绝它们；现在 AI 让生成大改动变便宜，但 review 和验证仍然昂贵。让 LLM 把一个大改机械拆成十几个合规小 PR，并不会真正解决问题，只是把成本转移到漫长 review 上。

因此，未来更重要的能力不是单纯加速写代码，而是加速评估代码。团队需要更多投入 CI/CD、规格、UX 测试、自动化验证和 AI 辅助 review。大多数大跳跃仍然会是坏主意，但如果生成成本足够低，快速尝试、快速拒绝、快速收敛就会变得可行。作者最后的态度很克制：不要滥用大跳跃，客户也不喜欢产品频繁在脚下变形；但当系统卡在深井里时，确实需要更高能量的一跳来脱困。

## 关键句意

- 小 PR 是稳定工程的好工具，但不是所有变化都能自然拆成小 PR。
- 退火的直觉适合成熟系统的稳定阶段，不适合所有探索阶段。
- AI 让“大规模尝试”的生产成本下降，却没有自动解决 review 与验证瓶颈。
- 大改动的价值在于探索，而不是直接进入生产。
- 未来更值得投资的可能是 AI 辅助 review，而不只是 AI 辅助开发。
