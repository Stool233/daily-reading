# 阅读笔记

## 一句话总结

AI 让软件团队重新拥有“高能量大跳跃”的能力，但真正稀缺的能力会从写代码转向验证、review、拒绝和收敛这些大跳跃。

## 关键概念

- **模拟退火**：先用大步探索，再逐渐降低能量、缩小步长，使系统趋于稳定。
- **高能量变化**：大范围、互相关联、用于探索系统新形状的改动。
- **低能量变化**：小 PR、小修补、局部变更，适合成熟产品的稳定维护。
- **局部最优**：系统因为所有变更都太小而无法跨过结构性障碍，只能继续优化现有形状。
- **AI 生成成本下降**：大改动更便宜了，但不代表大改动更安全。
- **review 瓶颈**：当写代码变容易，审代码、验证规格、评估用户影响会变成主要成本。

## 文章主张

1. 小 PR、单一职责、易 review、测试覆盖都是有用的软件工程实践。
2. 这些实践在成熟系统里尤其重要，因为稳定性和用户信任已经是产品资产。
3. 但把小步变化当成普遍真理，会让团队在需要系统重塑时陷入局部最优。
4. 有些功能必须先端到端地长出来，才能知道合理的数据结构、语义边界和拆分方式。
5. AI 辅助编码让大规模探索变便宜，却把压力转移到 review、测试、规格和产品判断上。
6. 未来团队应该更重视 AI 辅助 review 和自动化验证，而不是只追求更快生成代码。

## 我的理解

这篇文章很妙的地方在于，它没有简单站队“大 PR”或“小 PR”。作者真正反对的是把阶段性工具绝对化。小 PR 是低能量阶段的好工具，适合已经找到形状、正在硬化结构的系统；但在探索阶段，系统的核心问题不是“如何避免破坏晶体结构”，而是“晶体结构到底应该长成什么样”。

AI 编程让这个问题更尖锐。过去大改动很贵，团队天然不会随便尝试；现在大改动的生成成本下降，尝试本身不再那么可怕。但这也暴露出旧流程的薄弱点：我们没有足够好的机制快速判断一个大改是否值得保留。把大改切成很多小 PR，只是让它看起来符合流程，并不一定更容易理解整体设计。

对 agent 工程来说，这篇文章是在提醒我们：不要只优化“生成代码”这一端。真正的杠杆在于让 agent 帮团队完成预审、规格对照、测试缺口发现、架构影响分析和 UX 风险评估。写代码便宜以后，review 质量会成为系统质量的中心。

## 对软件团队的启发

- 按产品阶段选择变更策略：新产品允许更高能量探索，成熟产品需要更低能量硬化。
- 对探索性大改，不要过早要求它按最终 review 顺序拆分；先让端到端语义跑通。
- 大改进入 review 前，应有自动化预审：测试、lint、规格检查、迁移影响、性能和 UX 风险。
- 小 PR 规则应该允许例外，并要求例外给出整体设计解释，而不是机械压缩行数。
- AI 生成的大改应被视为实验分支，默认需要强验证和快速拒绝通道。

## 可延伸思考

- 团队能否定义“高能量变更模式”，明确何时允许大跳跃、如何验证、何时降温拆分？
- 大 PR 的 review 是否应该从逐行阅读转向先审设计、规格和行为差异？
- AI 预审工具应该输出什么，才能真的减轻 human reviewer 的负担？
- 如何避免“AI 生成很多大改”把组织拖入更深的 review 债务？
- 对成熟产品而言，哪些局部最优值得用高能量改动去跨越？

## 待补充问题

- Aperture 的 quota 功能后来如何被测试和验证？
- Tailscale 内部是否有明确区分 exploratory branch 和 production PR 的流程？
- AI-assisted review 是否会比 AI-assisted coding 更早成为成熟团队的刚需？
- 什么样的规格最适合帮助 reviewer 判断一个大改是否方向正确？
