# Anthropic 如何用 Claude 实现自助式数据分析

> 发布日期：2026-06-03

## 开篇：自助分析的老问题与新风险

文章从数据团队长期面对的痛点说起：业务方希望自己问问题、拿答案，不想每次都排队等数据科学家或数据工程师。但传统的自助分析做法往往会制造新的复杂度。

一种做法是给非技术同事暴露很宽、很扁平的表。短期看，这能降低 SQL 和数据建模门槛；长期看，随着业务扩张，表和视图会越来越多，指标定义会重叠，计算口径会不一致，大家仍然不知道应该用哪一个。

另一种做法是为不同用户或团队创建相对隔离的分析环境。这能减少中心团队压力，但容易漏掉大量长尾业务问题，并导致 dashboard 和 metric 不断膨胀。团队各自为政，最终形成新的孤岛。

LLM 看起来提供了第三条路：让用户用自然语言提问，让 Claude 这类 agent 自动理解问题、选择数据源、写查询并返回结论。文章提醒，这条路虽然强大，但也可能带来“精确感幻觉”。答案看起来非常确定，但用户反而离底层数据模型、文档、治理规则和专家判断更远了。

Anthropic 的核心判断是：自助分析 agent 的准确率，主要不是 SQL 生成能力问题，而是上下文和验证问题。真正困难的是把用户的业务语言稳定映射到正确、最新、受治理的数据实体，并确认 agent 的分析路径没有偏离。

文章提到，Anthropic 内部已经用 Claude 自动化了大部分业务分析查询，并达到较高的总体准确率。这样做的价值不是替代数据团队，而是把重复、零散、低杠杆的请求交给 Claude，让数据科学团队把时间投入因果建模、预测和机器学习等更战略性的工作。

## 分析任务为什么不同于软件任务

文章首先区分了 coding agent 和 analytics agent。

软件开发通常是开放式问题。一个需求可以有多种正确实现，模型的创造力是优势；同时，类型系统、测试、lint、review 等机制可以在一定程度上约束幻觉。

业务分析不一样。很多问题只有一个正确答案，而且这个答案依赖一个正确的数据源、一个正确的粒度、一个正确的时间窗口、一个正确的过滤规则和一个正确的业务定义。更麻烦的是，通常没有一个简单、确定的测试能证明答案完全正确。错误答案可能非常像真的。

因此，自助式 agentic analytics 的核心复杂度来自数据歧义。用户问“活跃用户”“收入”“某次发布后的留存”“某渠道转化率”，这些词背后都可能对应多个表、多个字段、多个指标定义和多个排除规则。agent 必须知道应该选哪一个。

文章把大多数错误归为三类。

第一类是业务概念到数据实体的映射歧义。比如“活跃用户”到底按登录、付费、创建内容还是调用 API 计算？是否排除欺诈用户？使用多长的回看窗口？当数据模型里有大量可能相关的字段时，agent 很容易选择一个看似合理但并非治理口径的对象。

第二类是数据过时。数据源、业务定义、schema、文档和 dashboard 都会不断变化。如果 agent 依赖的说明、技能文件或缓存上下文没有同步更新，就会返回微妙但错误的答案。

第三类是检索失败。正确答案可能已经存在于语义层、文档或历史分析里，但搜索空间太大，agent 没有找到它。这里的问题不是“没有信息”，而是“信息没有以 agent 可稳定发现和使用的方式组织起来”。

## Anthropic 的 agentic analytics stack

Anthropic 用一套分层的数据分析栈来分别处理这些问题。

最底层是数据基础。它包括数据仓库中的模型、转换、测试、表，以及描述这些对象的元数据。文章强调，传统数据工程的基本功并没有因为 LLM 出现而过时：维度建模、左移测试、关键链路的新鲜度检查、完整性检查、血缘和质量监控仍然重要。

变化在于最终用户。过去数据模型主要给数据专家使用；现在 agent 会代表不同数据素养的用户查询仓库。用户可能无法判断底层口径是否正确，因此数据模型本身必须对 agent 足够清晰、足够受治理、足够可验证。

文章给出的实践包括四点。

第一，创建规范的 canonical datasets。最常见的失败是 agent 无法把“某产品的收入”这类业务概念映射到唯一正确的表、字段和指标定义。解决办法不是让 agent 在更多表中自由搜索，而是减少候选项，维护少量、强治理、可发现、单一事实来源的数据集，并逐步废弃近似重复对象。物理 rollup 和 cache 可以继续存在，但它们应该从 canonical model 机械派生，而不是作为并列事实来源存在。

第二，强制执行标准。治理如果只停留在文档上，很快就会退回“多个候选项都像对的”的状态。Anthropic 的做法是通过工具路由、CI 检查和组织要求共同执行标准：agent 优先使用治理层，绕过治理层的变更需要在 review 中失败，下游团队默认基于受治理层构建。

第三，把相关资产放在一起维护。数据模型、语义层、参考文档、canonical dashboard 定义和 skill 文件如果分散在不同地方，就很容易不同步。Anthropic 的防线是共仓与 CI：如果某个模型变更会破坏下游 dashboard 或使某个指标文档失效，CI 应该在同一个 PR 中暴露问题，并要求同步修复。

第四，把 metadata 当作产品。表和列描述、指标定义、粒度说明、有效值范围、血缘、ownership、模型分层等，都应该像代码里的 README、类型签名和 docstring 一样被认真维护。好的治理不是形式主义，它为 agent 提供选择正确数据集所需的上下文。

## 可信来源：让 agent 先找“正确答案所在的位置”

如果数据基础是仓库本身，那么可信来源就是 agent 用来导航仓库的参考界面。这一层的目标是把用户问题中的业务概念变成具体、受治理的数据实体。

最高优先级是语义层。语义层保存经过编译的指标和维度定义。如果问题能映射到已经定义好的指标，agent 应该调用语义层，而不是自己写 SQL 拼口径。这样得到的数字和公司其他系统显示的数字一致。文章还提到一个反例：用 LLM 从原始表和查询日志自动生成指标定义，看起来很诱人，但可能会把原有歧义也编码进去。更好的做法是让 Claude 帮助起草文档，但指标定义仍由人类负责。

其次是血缘和转换图。当语义层没有覆盖某个问题时，agent 可以借助 lineage 和表引用频率判断哪些上游模型支撑某个概念、哪些模型已经废弃、哪些表具有相同粒度。这样，问题从“我不知道这个指标”变成“我知道应该从哪个治理模型聚合”。

历史查询语料听起来很有价值，因为它记录了过去已经回答过的问题。但 Anthropic 的消融实验发现，直接把大量 dashboard、notebook 和历史 SQL 暴露给 agent，准确率提升不到一个百分点。原因是非结构化检索不能稳定地把一个新问题映射到正确先例。真正有效的做法是把历史查询蒸馏成按业务域组织的参考文档和可复用分析模式。历史 SQL 应该是策展材料，而不是 agent 直接搜索的事实来源。

最后是业务上下文。文章认为这是很多团队最容易低估的一层。不了解业务的 agent 会回答用户字面上问的问题，却不一定回答用户真正想问的问题。它不知道“Q2 发布”指哪个产品，不知道两个团队对同一个词的定义不同，也不知道某个问题是因为周四有董事会会议。Anthropic 会接入公司知识图谱，包括文档、roadmap、决策记录和组织结构，让 agent 能处理这类环境性引用，并在必要时提出更好的澄清问题。

这一节的共同主题仍然是文档质量。Claude 可以帮助补足文档，例如起草列描述、根据查询模式提出指标说明、在 CI 中标记未记录模型。但最终的策展和所有权必须由人负责。

## Skills：把资深分析师的流程写下来

在这篇文章里，Skills 是 agent 的程序性知识。可信来源告诉 agent“指标是什么意思”，Skills 则告诉 agent“应该按什么顺序查、如何处理歧义、怎样完成一个可信的分析”。

Anthropic 的一个关键经验是，Skills 对准确率提升很大。重要的不是“写更多 prompt”，而是用 Skills 让 agent 在写查询之前缩小搜索空间，并强制它优先使用正确的来源。

文章描述了一种成对的 skill 设计。

第一类是 knowledge skill，像一个顶层路由器。它告诉 agent 先尝试语义层；如果语义层不覆盖，再按业务域加载少量精心维护的参考文件。这种设计针对的是检索失败：不要让 agent 在百万字段级别的仓库里自由搜索，而是先把问题路由到几十个可治理、可维护的 reference docs。

第二类是分析执行 skill。它编码资深分析师会遵循的流程：先澄清问题，再找来源，运行查询，然后通过对抗式 review 检查假设和 SQL，最后给出带有方法、限制和来源说明的结果。它还可以包含常见分析模式，例如留存曲线、rate decomposition 和漏斗分析，避免每次重新发明。

参考文档本身也要面向 LLM 检索来写。好的 reference doc 会描述表的粒度、范围、排除规则、使用场景、不能使用的场景、join key、必需过滤器、常见陷阱和跨域引用。它不应该堆满容易过时的查询配方，而应该把资深分析师会提醒你的判断规则写清楚。

Skill 维护必须成为一等工程工作。数据模型每天变化，如果 skill docs 不维护，几周内就会变错。文章提到，Anthropic 曾观察到离线准确率从发布时的高水平在一个月内明显下降，直到他们把维护当成工程问题处理：skill markdown 和 transformation models 放在同一个仓库，修改 reporting model 的 PR 如果没有触碰相关 skill 文件，就会被 code-review hook 标记。现在大多数数据模型 PR 会同时包含 skill 更新。

另一个原则是跨界面一致。用户可能在 Slack、IDE、dashboard 工具或独立 agent 会话里问同一个问题，答案应该一致。Anthropic 通过一个 canonical data repo 管理技能内容，并在合并后同步到不同使用界面，避免不同表面各自漂移。

## Validation：知道系统到底有没有变好

验证层的作用，是发现三类失败模式中哪一类仍然在泄漏。

很多团队会搭建复杂的 agentic analytics 环境，却没有流程评估准确率。文章认为，离线 eval 是最低限度的起点。离线 eval 可以理解为问题和答案对，类似机器学习里的离线测试：它不等于线上表现，但能暴露关键空洞。

Anthropic 使用两类离线 eval。第一类来自 dashboard：Claude 可以根据常见 dashboard 自动生成问题，再由人验证，覆盖最常见的 stakeholder 问法。第二类覆盖长尾：给 Claude 业务上下文、roadmap 和 table docs，让它生成领域内可能出现的问题，再形成测试集。每当 stakeholder 在线纠正 agent，这个纠正也可以变成候选 eval。

文章给出几条 eval 实践。

首先，ground truth 不能漂移。直接拿实时数据写 eval，一旦底层数字变化，答案就过期了。可以把 eval 锚定到快照日期、稳定事实表，或者让 grader 评估 agent 的查询逻辑而不是最终数字。相关测试应该接入 CI，使影响依赖的 PR 触发对应 eval。

其次，eval 结果要像 telemetry 一样存储。每次运行都应该记录 skill version、git SHA、model ID、断言通过情况、token 成本和耗时。这样“这个改动有没有帮助”就可以用查询回答，而不是靠争论。

再次，发布应该按业务域 gated。某个 domain owner 不能在自己的 stakeholder 面前宣布 agent 可用，直到该领域 eval 达到约定阈值。这会迫使团队在用户看到失败之前修复 reference docs。

最后，eval 数量要与业务域复杂度匹配。越复杂的业务和数据模型越需要覆盖；同时，超过某个数量后收益会下降，尤其是模型能力提升后，少量高质量 eval 可能就能捕捉大部分风险。

## Ablation：用固定 eval 集替代争论

文章的消融实验部分很值得复用。Anthropic 对 skill 的结构性决策使用固定离线 eval 集验证：要不要暴露某些来源、是否值得引入 review sub-agent、两个 skill 应该合并还是拆开，都通过只改变一个因素来比较通过率。

一个重要的负结果是：让 agent 直接 grep 大量 dashboard、transformation 和 analyst-notebook SQL，几乎没有提升准确率。更有意思的是，他们检查了错误样本后发现，很多时候正确答案确实存在于语料中，agent 也读到了相关内容，但仍然没有正确使用。这说明瓶颈不是访问权限，而是结构化导航：agent 需要被引导到正确实体和正确方法。

文章建议每次有意义的 skill 修改，都在相关 eval slice 上跑 before/after，并把结果写进 PR。这样“我改进了文档”就不再是主观判断。它也能捕捉常见反直觉情况：某个出于好意的补充可能让文档更长、更难检索，反而降低准确率。

负结果同样要记录。Anthropic 提到过一些没有奏效的尝试，例如继续堆叠更多文档精修轮次，或者把对抗式 reviewer 换成更便宜的模型。记录这些失败，可以避免下一位同事重复同样实验。

## Online validation：生产环境里的防线

离线 eval 不够，还需要线上验证。

第一种做法是对抗式 review。Anthropic 使用 Claude skill 主动挑战最终答案背后的假设，在 eval 中换来更高准确率，但也带来更多 token 成本和更高延迟。这里的工程选择很清楚：不是所有请求都值得花这个成本，但对高风险或高影响分析，它是值得考虑的。

第二种是 provenance footer。每个回答都附带来源层级、数据新鲜度、模型 owner 和 review 信息。例如答案是来自语义层、策展参考还是原始表探索，底层数据更新到哪一天，哪个团队负责。这个 footer 不能让错误答案自动变正确，但它能帮助使用者判断信任程度。如果某个答案来自原始表且新鲜度未知，用户就知道在向上汇报前要额外核验。

第三种是数据质量检查。即使 agent 选对了字段和用法，底层数据本身也可能有问题。因此系统应该检查引用字段是否最新、完整、是否有异常。

第四种是被动监控。Anthropic 持续跟踪两个生产信号：agent 查询中有多少通过语义层解析，以及回答中出现用户纠正语言的比例。这些信号会和离线通过率一起定期 review。

第五种是主动收集纠正。一个定时 agent 会扫描 stakeholder 频道中的纠正语言，为相关 reference doc 起草一行修复，并开 PR 给 domain owner。这个流程被设计得很普通：改 markdown、merge、自动同步到各处。正是这种普通，降低了维护成本。相同纠正也会反馈进离线 eval 集。

文章也坦诚指出，最难完全捕捉的是沉默的错误。答案错了，但看起来合理，用户也没有提出异议。Anthropic 的缓解方法包括 provenance footer、面向领导层材料的人类签核，以及每天用领域顶级 KPI 对照被认可 dashboard 做 sanity check。但他们还没有彻底解决这个问题。

## 从哪里开始

如果从零开始，文章建议不要一上来搭全套复杂系统。少量 canonical datasets、几十个离线 eval、一个薄的 knowledge skill，就能捕捉大部分收益。其他机制可以在这些基础设施建立后逐步增加。

不同组织应该根据自身情况取舍：今天的正确率和未来模型能力进步哪个更重要？业务复杂度未来会怎样变化？输出面向的是能识别错误的数据专家，还是不了解底层模型的业务用户？愿意为准确率提升承担多少成本和延迟？对访问控制和内部数据隐私的舒适区在哪里？

不管路线如何，最大的收益都来自持续处理三类失败：把歧义压缩成唯一受治理答案，让这个答案容易被发现，并在答案过时的时候及时标记出来。

## 术语对照

- **Self-service analytics**：自助式分析 / 自助式数据分析
- **Agentic analytics**：Agentic 数据分析 / 由 agent 驱动的数据分析
- **Semantic layer**：语义层
- **Canonical dataset**：规范数据集 / 单一事实来源数据集
- **Source of truth**：可信来源 / 事实来源
- **Lineage**：血缘
- **Grain**：数据粒度
- **Freshness**：数据新鲜度
- **Ablation**：消融实验
- **Provenance footer**：来源说明尾注 / 溯源尾注
- **Offline eval**：离线评估
- **Online validation**：线上验证
- **Reference docs**：参考文档
- **Domain owner**：业务域负责人 / 数据域负责人

## 核心脉络

1. 自助分析的难点不是让模型写出 SQL，而是让模型选择正确、最新、受治理的数据实体。
2. 大多数错误来自业务概念映射歧义、数据过时和检索失败。
3. 数据基础仍然重要：canonical datasets、CI、metadata、lineage 和 ownership 是 agent 准确性的底层条件。
4. 可信来源要分层：优先语义层，其次 lineage 和治理模型，再将历史 SQL 蒸馏成结构化文档。
5. Skills 是程序性知识，负责把资深分析师的工作流写成 agent 可执行的路由和检查流程。
6. Skill docs 必须和数据模型共仓维护，否则准确率会随时间快速衰减。
7. Eval 结果要作为 telemetry 存储，PR 级别做 before/after，负结果也要记录。
8. 线上答案要带来源、数据新鲜度、owner 和 review 信息，帮助用户判断可信度。
9. 沉默错误仍然是最难的问题，需要 provenance、人类签核和关键 KPI sanity check 共同缓解。
